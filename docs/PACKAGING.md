# Packaging and project installation

This is a private, unpublished development package. This document describes the
actual installer and the local packaging checks. It does not select a project
license, authorize redistribution of the research corpus, or establish that a
particular agent application's trust and discovery flows have been exercised.

## Skill reference boundary

Installed skills must resolve every local link inside the installed skills
directory; the packaging test enforces this. The science, robotics and healthcare
source maps name `research/manifests/science.json` and
`research/manifests/docs-public-science.json` as repository-only provenance in
plain code text; those ledgers are not bundled. Likewise `src/components.mjs`
(in `component-integration`) and `research/dossiers/software-browser-skills.md`
(in the LangGraph/n8n entrypoints) appear as plain code paths, not attachments.
Research dossiers and ledgers are development-only context and must never be
bundled to repair a broken link.

## Package boundary

The authority for what enters the archive is the npm file inventory, not the Git
ignore file. The first audit found Python bytecode under
`adapters/langgraph/__pycache__/` and UI evidence under `web/artifacts/` in the
archive, so `package.json` selects the three runtime UI assets explicitly:

```json
["web/index.html", "web/app.js", "web/style.css"]
```

The adapter entries include source, runtime support and documentation, while
excluding generated bytecode and evidence directories:

```json
[
  "adapters/index.mjs",
  "adapters/langgraph/*.mjs",
  "adapters/langgraph/*.py",
  "adapters/langgraph/*.md",
  "adapters/langgraph/requirements.in",
  "adapters/langgraph/requirements.txt",
  "adapters/n8n/*.mjs",
  "adapters/n8n/*.md"
]
```

The other entries select `bin/foundry.mjs`, flat `src/*.mjs` modules, the workflow
schema, portable skill `.md`/`.json`/`.txt` files, explicitly named documentation files
and the five existing example files. Both example workflows (`hello.json` and
`incident.json`), the incident world fixture, and the batch task/suite companions
are retained. The package test requires the public export targets and every
current adapter source/support file. No `.npmignore` is needed for this boundary.

Verify the result using npm's inventory and the actual extracted archive. Keep
`corpus/`, `research/`, `evals/`, mutable `.foundry/`,
upstream license payloads, model weights, raw model responses, screenshots and
compiled bytecode out of the archive. Preserve the original acquisition records
and upstream notices in the research workspace. The test compares packed content
hashes against the 218 deduplicated license-file records in the acquisition
ledgers; this is a bounded payload check, not a license audit or general copied-code
detector. The existing `private: true` value remains unchanged.

`README.md` is included, and the integrity test requires the packed bytes to match
the source README. This guide and
[ARCHITECTURE.md](ARCHITECTURE.md) document the available local interfaces.
The repository has a lockfile; npm's package inventory did not include
`package-lock.json` or an npm shrinkwrap. Exact direct pins therefore do not by
themselves freeze a consumer's transitive package-manager resolution.

## Run the integrity checks

From the source repository with its existing dependencies:

```sh
node --test tests/packaging.test.mjs
FOUNDRY_PACKAGING_E2E=1 node --test --test-concurrency=1 --test-reporter=tap tests/packaging.test.mjs
npm run check
```

The default run performs the reference audit, provenance checks and their
negative-control fixtures; staged integration is explicitly skipped. The opt-in
run uses one package archive and five sequential local stdio processes.
Each subprocess has a 15-second ceiling; MCP requests have a
five-second timeout; the parent test has a 90-second ceiling. No browser, model,
upstream runtime or network service is launched. npm uses offline mode, disabled
lifecycle scripts, a temporary cache and two separate empty configuration files.
The child commands also receive a temporary home/configuration directory rather
than the operator's home. No global npm install or client settings are modified.

The staged distribution reuses this repository's already-installed Node
dependencies through one temporary `node_modules` symlink and checks their direct
versions against the package pins. This establishes packed-source operation under
that dependency set. It is **not** a clean npm installation from a registry, a test
of all transitive dependency resolutions, or agent-application integration.

Every staged run writes a new directory beneath:

```text
evals/runs/packaging-evidence-<unique-id>/
  packaging-report.json
  pack-dry-run.json
  pack-actual.json
  source-coverage.json
  contrare-research-workflow-foundry-0.1.0.tgz
  commands/001.json
  <client>-mcp-execution.json
```

`packaging-report.json` contains per-check outcomes, exact source hashes before and
after, packed-file hashes, tarball SHA-256, command exit codes/timing, installed
configuration, link failures with file/line/target, and MCP read counts. The final
gate also requires source stability. The snapshot includes every runtime module,
adapter source/support file, skill, example, published documentation file and the
README when present. The extracted archive must have the same inventory as npm
and the same bytes as the corresponding source files. Each command has a separate
stdout/stderr/exit receipt; each client's validate/save/run/inspect calls have a
separate protocol receipt. The tarball itself is retained. Reports from failed
runs remain available.
The test normally deletes only its own staging directory. Setting
`FOUNDRY_PACKAGING_KEEP_STAGE=1` retains that directory for an explicit quality
scan and records the exact path for subsequent cleanup.

The reference checker visits every Markdown file recursively. It covers the
inline/image links, reference definitions, file fragments and explicit
`references/...` code paths used by the current skills. Missing targets, missing
heading anchors, unresolved named references and unsupported destination syntax
are failures. HTTP URLs are preserved but are not fetched by this zero-network
packaging test. It is not a complete CommonMark implementation.

## Install the packed or source CLI into a project

The installer is the explicit `install` command in `bin/foundry.mjs`; it is not an
npm install lifecycle hook. The selected project directory must already exist.
These example placeholders must be replaced with the actual paths:

```sh
node /path/to/workflow-foundry/bin/foundry.mjs install \
  --project /path/to/task-project --client opencode --dry-run

node /path/to/workflow-foundry/bin/foundry.mjs install \
  --project /path/to/task-project --client opencode
```

`--client` accepts `generic`, `opencode`, `claude`, `cursor`, or `codex`.
`--no-hooks` suppresses the optional OpenCode/Claude advisory hooks. The preview
reports changes without writing skill/config files. An installation returns an
ID, changed-file count, command and journal path. Backups and restoration data
live in the project's `.foundry/install/<id>.json`; the installer adds
`/.foundry/` to that project's `.gitignore`.

| Client option | Skill destination | Generated MCP file | Optional hook |
|---|---|---|---|
| `generic` | `.agents/skills/` | `workflow-foundry.mcp.json` | None; import this template into the actual client |
| `opencode` | `.agents/skills/` | Existing `opencode.jsonc`, otherwise `opencode.json` | `.opencode/plugins/workflow-foundry.js` |
| `claude` | `.claude/skills/` | `.mcp.json` | `.claude/settings.json`, `PostToolUse` matching `Write\|Edit` |
| `cursor` | `.agents/skills/` | `.cursor/mcp.json` | None |
| `codex` | `.agents/skills/` | `.codex/config.toml` | None |

The 14 skill directories use progressive Markdown references and JSON companions.
Later construction/repair references change the exact file count; the current
archive and installed-file receipts record it. Copying includes nested `.md`, `.json` and `.txt` files;
source symlinks are rejected. Existing differing skill contents or conflicting
MCP entries stop installation. Both `opencode.json` and `opencode.jsonc` present
together are treated as ambiguous. Generated settings preserve compatible
existing values. Updating an installed skill is not an implicit overwrite flow.

The resulting configuration points to an **absolute Node executable and absolute
CLI path**, plus the exact project workspace. It is therefore project-scoped but
not relocatable: moving the distribution or changing the Node installation can
invalidate it. Uninstall using the existing receipt before deliberately
reinstalling from a new location; inspect conflicts instead of overwriting them.

## Actual MCP configuration shapes

These are the shapes emitted by `src/install.mjs`, with path placeholders for
readability. The staged tests execute the actual generated paths, including a
project directory containing a space.

Generic `workflow-foundry.mcp.json` and Cursor `.cursor/mcp.json`:

```json
{
  "mcpServers": {
    "workflow-foundry": {
      "command": "/absolute/path/to/node",
      "args": ["/absolute/package/bin/foundry.mjs", "mcp", "--workspace", "/absolute/task-project"]
    }
  }
}
```

Claude `.mcp.json` has the same entry with `"type": "stdio"`. OpenCode uses:

```json
{
  "mcp": {
    "workflow-foundry": {
      "type": "local",
      "command": ["/absolute/path/to/node", "/absolute/package/bin/foundry.mjs", "mcp", "--workspace", "/absolute/task-project"],
      "enabled": true,
      "timeout": 30000
    }
  }
}
```

Codex's managed TOML block is:

```toml
# BEGIN workflow-foundry managed MCP
[mcp_servers.workflow-foundry]
command = "/absolute/path/to/node"
args = ["/absolute/package/bin/foundry.mjs", "mcp", "--workspace", "/absolute/task-project"]
startup_timeout_sec = 20
tool_timeout_sec = 120
# END workflow-foundry managed MCP
```

The actual stdio checks initialize the server, list its tools, call
`foundry_skills`, read every skill Markdown via `foundry_read_skill`, and read
`foundry://schema/workflow`. They verify returned bytes against the installed
copy. For every generated configuration, the same connection validates and saves
the packed greeting example, executes it with an explicit object input and
inspects the completed run. An independent assertion reads the actual artifact
and compares its exact Unicode/literal text and SHA-256. An unknown shell tool
request must fail. No tool grants human-answer or approval authority. These checks do not
launch Claude Code, Cursor, Codex or OpenCode themselves, verify their trust
prompts, test their skill discovery, or execute their advisory hooks. Those
client-specific workflows require separate evidence.

The packed CLI is also exercised through `doctor`, `schema`, `skills`,
`capabilities`, `prompt`, `validate`, `run`, `inspect`, `evaluate`, and both
`export --target langgraph` and `export --target n8n`. The evaluation uses one
explicit diagnostic greeting case; it does not measure model quality. Adapter
exports contain their runtime/support files and remain unready without trusted
bindings. Generating these files does not launch Python or n8n or qualify either
target's execution semantics.

## Restore an installation

Use the ID returned by the original installation:

```sh
node /path/to/workflow-foundry/bin/foundry.mjs uninstall INSTALL_ID \
  --project /path/to/task-project --dry-run

node /path/to/workflow-foundry/bin/foundry.mjs uninstall INSTALL_ID \
  --project /path/to/task-project
```

Uninstall checks that affected files still match the installed or original bytes.
A user edit causes an explicit conflict; it is not discarded. The journal remains
as evidence. Each staged client begins with unrelated files and, where the client
supports merging, existing dummy servers and comments. Claude also has an inert
pre-existing hook. The test compares these bytes after uninstall. A second actual
installation must change zero files; uninstalling that empty receipt must restore
zero files before the original receipt is undone. Separate negative controls
exercise conflicting generic configuration, a symlinked Cursor directory and an
edited installed skill. All dummy settings remain inert. This verifies scoped
restoration, not wholesale deletion of a project or unrelated runtime history.

## Fresh dependency installation control

The separate repository command `node research/qualify-fresh-install.mjs` creates
a new npm consumer, packages the current source and installs that archive with
`npm install --offline --ignore-scripts --no-audit --no-fund`. It uses a pre-existing
npm content cache, isolated empty npm configuration files and a temporary home;
there is no online fallback, reused `node_modules` symlink or lifecycle hook.
It then checks exact product bytes and direct dependency versions, installs the
project-local OpenCode MCP configuration and executes its generated command through
an actual SDK client. The greeting artifact and event chain are checked independently.

Each invocation preserves its archive and commands under an ignored `.foundry/`
directory. Only a source-stable passing report qualifies its own archive. It is
not a clean machine, registry availability check, universal transitive-resolution
guarantee or full OpenCode application discovery/trust test.
