**Approach:** each incident has one owner instance. On every tick the owner replays its whole business history rule by rule into a timeline of incident snapshots. It runs the SLA engine at each change and recomputes all business time from the calendars from scratch. It then derives every effect the rules require, each with a stable key and its window, and emits the ones that are due and not yet committed.

**Self-tests:** written from the spec only, in `/var/tmp/foundry-work/e7-blind/s1/`. They run against a fake host I wrote from CONTRACT.md, not the bed's host, and use invented fixture data. 24 tests pass.

Citations below are to SPEC-E.md (§ / R / S) and CONTRACT.md (C§).

## Routing and instances
1. **Owner per incident.** The instance that records an incident (R1.1, R1.2), or the go-live instance (§3.6), owns it and declares its number as `decisions.subject` on every tick.
   - A message that starts a new instance looks for an open instance with that subject (`ctx.instances`). If it finds one, it returns `merge`.
   - If there is no open owner but the incident exists in `itsm.incidents`, the instance declares the subject and priority, emits nothing, and returns `close`. This covers duplicates and messages about closed incidents: "changes nothing" (R1.4, R3.3, S9).
   - If the incident does not exist, `subject: null` and `close` (§1 Routing, §3.3).
2. **No optional notices.** `unknown-incident` is never sent (§3.3 and S9 make it optional).
3. **Priority on merge ticks.** `decisions.priority` on a merge tick comes from the incident record at round start. It is adjusted when the merged message would change it: a resolver `reclassify`, or a joining alert that is more urgent (§1 Decisions). The owner's own ticks report the priority from its replay.
4. **Closing the owner.** The owner closes itself only once the incident is closed or cancelled and every required effect has a final result. After that, later messages are "changes nothing" instances (C§3.1 `close`).
5. **Same-round duplicate owners.** If two owners for one subject were opened in the same instant, the one with the higher instance id yields and closes from its second tick on. Its first-tick effects carry the same keys and arguments, so the systems do not apply them again (C§3.3).

## Normalisation (raw keys, C§3.2)
6. **Incident numbers** are trimmed, have one leading `#` removed, are trimmed again and upper-cased (§3). The incident number is `INC-` plus the report or alert id, normalised the same way. The id itself is kept trimmed in `source.id` and `linkAlert`.
7. **Lookups.**
   - CI: case-insensitive match on id, then name, then alias (§3.1). Alert `ci` is resolved the same way.
   - `callerId`: matched on user id or email.
   - `toGroup`: matched on group id or name.
   - Report `category` is lower-cased to the four values §3.1 lists.

## Transitions (R8.2, R3.2)
8. **Valid transitions only.** Resolver updates are applied only along R8.2. Anything else changes nothing and records nothing.
   - `accept` only from `assigned`.
   - `hold` only from `inProgress`; a hold while already `onHold`, for example a change of reason, is ignored.
   - `resume` only from `onHold`.
   - `reassign` and `resolve` from `assigned`, `inProgress` or `onHold`.
9. **Resolver `resume` during an `awaitingCaller` hold** is applied (R3.2 taken literally). §3.4 describes `resume` as following holds that were not waiting for the caller, so this is a possible divergence point.
10. **Other hold reasons** behave like `awaitingVendor` (§3.4). Only `awaitingCaller` triggers R6.1.
11. **Reassigning to the same group** is still recorded (`itsm.assign`, notice). It is not a change of `assignmentGroup` for R4.2 reset.
12. **Joining-alert reclassification.** R1.3 keeps impact, takes the alert's urgency when it is smaller, and uses R2.2 with the edition at the alert time. Like any R2.3 change, it can be the moment priority "first becomes 1" (R7.1).

## Ordering within an instant
13. **Phases.** Events at one instant are applied in delivery order: round 1 before merged events of round 3, then `(source, id)` as C§3.6 orders deliveries. The SLA engine (R4.2, S5) runs after each delivery batch ("phase"), not once per instant, because a round-3 merge cannot be known in round 1.
   - SLAs attached in an earlier phase at the same instant count as "attached before" in later phases.
   - "Held just before" and "the reset field changed" compare against the state before the phase.
   - Within a phase, R7.3 mootness is checked after each event, so an answer that counted before a withdrawal still counts (S16).
14. **Deadline consequences** form their own phase after every event phase at the deadline instant. These are the R6.3 no-reply close, the R6.5 auto close and the R7.2 declaration.
    - The phase is taken only once `now` is past the deadline, at the deadline plus 1 minute.
    - Its records are dated at the deadline, and the SLA records it causes take the closure's window (R4.5 last paragraph, S1, S10).
    - At the approval deadline, an R6.3 closure is applied before the declaration, so it makes the approval moot (S16).

## SLA engine (R4)
15. **Editions.** "Start held before" is evaluated with the current edition's definition. A reset re-attach and the attach caused by a reset-field change use the definition in force at that instant (S15). Existing SLAs keep the definition from their attach instant (R4.3).
16. **Generation** counts every earlier SLA of the definition on the incident, in any stage, including migrated records (R4.3).
17. **Retroactive pause intervals** are evaluated over the replayed snapshot history with the definition from the attach edition (S6).
    - If the last interval runs up to `x` and the pause condition still holds at `x`, the SLA attaches paused from that interval's start, with no resume (S14).
    - Each past resume carries D as of its own `at` (S13).
18. **Planned breach.** `sla.start.plannedBreachAt` is counted from `startAt` as if the SLA were never paused, even when it attaches paused (S13). It is `null` only if the target is never reached within about 5 years of the schedule.
19. **Calendars.**
    - An interval is `[start, end)` in local wall-clock time. `end <= start` crosses midnight, and `"24:00"` is the next midnight.
    - A holiday closes its whole local date, or `[from, to)` of it.
    - A local time that is skipped at a clock change maps to the instant of the jump.
    - `businessHours: "24x7"` is all day, with holidays still applied.
    - Schedule source `service` or `assignmentGroup` with no calendar id means 24×7 with `schedule: null`.
    - A calendar id that does not resolve is recorded but computed as 24×7.
    - A floating calendar with no zone from its sources is computed in `Europe/Amsterdam` but recorded as `timezone: null`.
20. **Thresholds.** `floor(target × percent / 100)` minutes of business time, reached at the first instant business time equals it. A threshold reached exactly at a closing time is reached there (S4).
    - A threshold reached at the instant of a stop, cancel or pause counts (S3).
    - Percentages above 100 are sent if reached before the end.
    - A threshold of 0 is reached at `startAt`.
21. **Escalation recipient.** `to` is resolved at the due instant, `max(threshold instant, attach)`, against the state after every change at that instant. For example, a reassignment at the same instant sends a `group` notice to the new group (R5.2). Escalations with no resolvable address are skipped.
22. **Breach.** Breach is recorded once at D when D is at or before the end; window from `max(D, attach)` (R4.5, R4.6, S2). It is ordered before a stop or cancel at the same instant, because the `sla` system refuses a breach after the end (§2).

## Callers, closure, approval (R6, R7)
23. **Business time B.** Uses the policy calendar from the edition at the clock start: h for a hold, r for a resolution. One business day is `businessDayMinutes`. If the calendar is missing, B is wall-clock time.
24. **Withdraw on an incident with no caller** (opened by an alert) cancels it, but no notice is sent because there is no caller email. Alert incidents never get `resolved` notices (R6.4).
25. **Approval task.**
    - Created in the tick where priority first becomes 1.
    - `excludeUsers: [callerId]` only when there is a caller.
    - `answerSchema` requires `decision` in `approve` or `reject`.
    - `dueAt` is the deadline; `onTimeout: 'expire'` (its format is not specified).
    - The deadline is task creation plus `majorApprovalMinutes` of wall-clock time, not business time (R7.2). The policy edition is the one at creation.
26. **No re-ask.** R7.2 makes re-asking optional ("may"). An answer counts only if it carries `decision` equal to `approve` or `reject` after trimming and lower-casing. Free text, other values, timeouts, withdrawals and delegations are unusable or ignored, which leads to the deadline declaration unless the approval is moot.
27. **Approval moot.** Before the deadline: resolved, closed, cancelled, or priority no longer 1. At the deadline: only closed or cancelled (R7.3, S16). A priority that returns to 1 later is not a "first" time.

## Effects, keys, retries (§1, C§3.3)
28. **Keys.** One key per logical effect, built from the op, incident and instant. For SLAs the key uses the SLA id (and the instant for pauses and resumes); escalations use the percent; notices use template and occasion. Every retry reuses the key and the arguments stored at the first attempt.
29. **Ordering with `after`.** `after` keeps application order within a tick:
    - each incident's itsm ops are chained;
    - notices and SLA starts come after `itsm.create`;
    - each SLA's records are chained;
    - escalations come after their SLA start.

    If a predecessor from an earlier tick is still in flight, its dependents wait for its result.
30. **Results.**

    | result | handling |
    |---|---|
    | `rate-limited` | Re-issued at the result time plus `retryAfter` seconds, rounded up to a whole minute. |
    | 5xx, 400 (`invalid-args`, `field-renamed`), 404, `predecessor-failed` | Re-issued at once; arguments are renamed again from the current schema file. |
    | 409 | Final. |
    | `unknown` or `partial` | Checked with `ctx.status`: `committed` means done, `not-found` means re-issue, `pending` means check again a minute later. |
    | Anything else | Gives up after 8 attempts, or after 15 status checks. |

31. **Late effects.** An effect still due after its window is emitted late rather than dropped, so the records end up right (R8.1).
32. **API renames (§1).** Each canonical argument is written under the current schema's name. The order of checks is:
    1. an explicit hint on the property (`renamedFrom`, `formerly` or similar, or a mention in its description);
    2. the single unmatched property of a compatible type;
    3. the closest name.
33. **Editions (R0).** The local date is taken in `systemTimeZone`. Editions present on the instance's first tick count as published throughout; editions that appear later count from the tick that first sees them.

## Go-live (§3.6)
34. **Base state.** The migrated `itsm.incidents` record is the state at go-live. Migrated SLA records continue with their own `startAt`, pauses, schedule and zone. Their definition comes from the edition at `startAt`, or else the latest edition that has it. Recorded escalations and breaches are not repeated.
35. **Effects already due before go-live.** An effect whose window ended before go-live is not emitted. A notice whose window spans go-live (`awaiting-caller`, `resolved`, `major-incident`) is sent unless the export already shows it.
36. **Hold instant h** for an `awaitingCaller` hold, in order of preference:
    1. the export's last `awaitingCaller` hold message;
    2. the start of an open SLA pause;
    3. go-live itself.
37. **Earlier history** (for retroactive pauses) is approximated by replaying the export's hold, resume, reassign, resolve and caller messages on state, hold reason and group.
38. **Approval for a migrated P1 incident** is asked only if the incident opened less than 15 minutes before go-live and the export shows no task.

## Known limitations (views a single tick cannot have)
- **S8 race in one round.** An alert at the same instant as a resolve of the incident it would join cannot see the resolve: both land in round 1. It merges into the owner, which then refuses the link because the incident is not open (S8). The new incident that S8 implies is not opened.
- **Two alerts in one round.** Two alerts with the same CI and check at the same instant each open an incident; neither instance sees the other.
- **Unknown formats.** These output formats are not given in the arm files and were guessed:
  - obligations `{ id: 'wake:<instance>', kind: 'wake', anchor: <now>, dueAt, onDue: 'recheck' }`;
  - `humanTasks[].onTimeout`;
  - the payload of `humanTask.answered`, read as `taskId` plus `answer.decision`, with fallbacks;
  - the shape of the migration export (found by record shape);
  - the type of `ctx.files` (flat object, nested object, Map, array, reader function or directory path are all handled).
