# s3: blind E7 solver #3, notes

Written from the arm files only (`SPEC-E.md`, `TASK.md`, `CONTRACT.md`, `api/*.schema.json`) and the arm interface of
BED-CONTRACT v1.1 §3. No oracle, grader, reference policy, other solver or E7 source was opened. No model calls.

## Structure (different from a handler-per-event solver)

- **Event log, replayed.** Each incident keeps a compact log of business inputs (resolver updates, caller messages,
  joining alerts, task events) plus the facts the solver itself created (approval tasks and when). Every tick replays
  the log into an incident timeline: one snapshot per change instant. Deadline consequences are later sub-instants
  of the same instant (`sub 1` closures, `sub 2` the major declaration).
- **Obligations table.** The replay emits every effect the rules require: a deterministic key, canonical args, a
  window `[from, to]` and the key it must follow. The SLA engine (R4/R5) runs over the timeline's snapshots, then adds
  the time-driven records (breach at D, escalations at thresholds).
- **Scheduler.** It diffs the table against an effect ledger in carry (`sent | ok | retry | unknown | dead`). It emits
  what is due, in dependency order, using `after` when the predecessor is in the same output. It retries failures with
  the same key and arguments, and asks for one wake-up at the earliest future due instant. A key is never re-sent
  after it commits. Keys come from the effect's identity (incident, op, instant, values), never from the instance.

## Readings adopted where the spec left a choice

1. **Transitions (R8.2, §2 "itsm does not check transitions").** Accept only from `assigned`. Hold only from
   `inProgress`. Resume only from `onHold`. Resolve from `assigned|inProgress|onHold`. Anything else is ignored (W2
   noise), with no record. A resolver `resume` during an `awaitingCaller` hold is applied: R3.2 lists `resume`
   unconditionally and `onHold → inProgress` is a valid transition. The §3.4 wording ("after a hold that was not
   waiting for the caller") is read as a description, not a filter.
2. **Reassign to the current group while `assigned`** changes nothing, so nothing is recorded (R8.2 "record each
   change once"). From `inProgress`/`onHold` it is recorded: state, assignee and hold change. It is not a change of the
   reset field.
3. **R2.3:** a reclassify, or a joining alert, that leaves impact, urgency and priority unchanged is not recorded.
   Several changes at one instant get separate keys, because the key includes the new values.
4. **Deadline consequences (R6.3, R6.5, R7.2; S1, S10, S16).** Taken at the first tick strictly after the deadline
   (wake at D+1 min), dated at the deadline, and applied after every event of the deadline instant. A reply at D or a
   confirm at D2 counts. Closures come before the approval declaration at the same instant: a close at the deadline
   makes the approval moot (S16), a resolve does not. SLA records caused by these changes are dated at the deadline,
   with the change's window (R4.5 last paragraph).
5. **Mootness (R7.3, S16 "what happened first decides").** Checked after every event, in delivery order, not once per
   instant. Before the first task exists, a resolve, close, cancel or priority drop removes the need to create it.
6. **Approval (R7.1/R7.2).** Deadline = creation of the first task + `majorApprovalMinutes` (policy edition at that
   creation). The solver re-asks once per unusable answer, `answerRejected` or `withdrawn` on a counted task, while
   before the deadline and no answer has counted. The spec says "may"; this solver takes it. Only an `answered` event
   consumes a task: a later valid answer on a task whose earlier answer was rejected by the schema can still count. A
   `decision` other than approve/reject is unusable. The human task's `dueAt` is the approval deadline. `excludeUsers`
   is omitted when the incident has no caller (alert-opened).
7. **S8 tie (alert vs resolution in one instant).** An alert that may join an open incident is merged into that
   incident's instance. That instance judges "open at the alert's time" from its own complete log, after the instant's
   updates and deadline consequences. The resolve and the alert can both arrive in round 3. If the incident is no
   longer open there, that instance opens the alert's incident itself as a second incident. Its records carry its own
   number, and the assignment notice carries an owner tag (`ref`) so later inbound messages can find it.
8. **Notices without a recipient.** `awaiting-caller`, `resolved` and `incident-cancelled` go to the caller's email.
   An alert-opened incident has none, so no notice is sent; D and D2 still apply (R6.4 says so for D2; the same is
   adopted for D). `unknown-incident` is never sent (optional, §3.3/S9).
9. **Breach ordering (R4.6, S2, §2).** Inside an SLA's chain the breach record is placed before a pause, stop or
   cancel at the same instant, because the system refuses a breach after stop/cancel. A stop at D carries
   `breached: true`. Escalations depend only on the start record and may follow the stop or cancel, as §2 allows.
10. **Reset attach (R4.2 last paragraph, S15).** A change of the reset field also attaches a new generation of a
    definition whose earlier generation already completed (for example a response SLA stopped at accept, then a
    reassign), provided the start condition holds and the stop condition does not, in the edition in force then.
11. **R4.2 step 1:** the cancel condition is tested before `whenStartFails`. Reason `cancelled` beats
    `start-failed`, and either beats stop.
12. **Thresholds (R5.1).** `floor(target*percent/100)`. A threshold of 0 is reached at `startAt`. Percent > 100 is
    computed the same way, past D. `to` is fixed at max(threshold instant, attach instant), from the group snapshot
    in force then (R5.2). `incidentManagers` uses the policy edition at that instant.
13. **Retries (§1).** A rate-limited effect is retried at result time + `retryAfter`, rounded up to the minute. If that
    would leave the window and emission time + `retryAfter` would not, the latter is used. 5xx and
    `predecessor-failed` retry at the next tick. A 400 is re-issued with the names the current schema shows, at most 3
    attempts. 409 and other 4xx are not retried. An `unknown` result is settled with `ctx.status`. A same-instant
    `committed` status (round 3) unblocks dependants at once.
14. **Late obligations.** An effect whose window has already passed is still issued once (for example an
    `itsm.create` whose `[t, t]` attempt was rate-limited): R8.1 wants the records to end up describing what
    happened. Exception at go-live: obligations whose window closed before t0 are left alone (pre-t0 history is not
    this arm's).
15. **Go-live (§3.6).** The incident and its SLAs continue from their records: stage, pauses, breach, escalations
    already sent, generations. Hold start `h` for the R6.3 deadline comes from, in order: the latest pre-t0 `hold`
    message, the open pause of an SLA, the `awaiting-caller` notice time, else t0. A migrated P1 that is not major gets
    an approval task only if `openedAt + 15 >= t0`, since human tasks are not in the export. Pre-t0 snapshots for
    retroactive pauses are synthesised from record timestamps (approximate).
16. **Editions (R0).** The edition in force is chosen by the local date in `policy.systemTimeZone` (default
    `Europe/Amsterdam`). If none is in force yet, the earliest is used. Files are re-read every call, so editions that
    appear without an event are picked up.
17. **Time zones (R4.3, R6).** A floating calendar whose sources give no zone falls back to the system time zone. So
    does a floating service-desk calendar. Times are written at `+01:00` (§1 Time).
18. **Identifiers (§3, contract §3.2 "possibly mistyped").** Incident-number normalisation (trim, strip leading `#`,
    upper-case) is also applied to `reportId`/`alertId` when forming `INC-` numbers. CI lookup is case-insensitive
    over id, name and aliases (§3.1). Alert CIs are stored as the canonical id. Checks are trimmed and compared
    case-insensitively. The resolver update's `group` is not validated against the assignment group.
19. **Duplicates (R1.4, W1).** A repeated event id is ignored, and so is an identical payload at the same instant. Two
    deliveries of one report in the same instant create the incident with identical keys and args; at the next tick
    the instance with the higher id yields and closes.
20. **Instance close.** Only when every incident it runs is closed or cancelled and every obligation is committed or
    abandoned. A message for an unknown incident, a warning alert or a duplicate is answered with `close: true`.
21. **Hold reason missing:** recorded as `other`. **No priority row:** priority falls back to `impact+urgency-1`,
    clamped to 1–5. **Unreachable target** (no open time for 1200 days): `plannedBreachAt: null`, which the schema
    allows.

## Interface assumptions (shapes the arm files do not fix)

- Event types are recognised by the spec names (`incident.reported`, `alert.raised`, `caller.message`,
  `resolver.update`). The contract's generic `doc.received`/`message.received` are recognised by payload fields or
  `source`. `docs/<eventId>.txt` is only a fallback for missing report fields.
- `ctx.files` may be a flat path map, a `Map`, a nested tree, a `{read, list}` object, a reader function or a directory
  path.
- Obligation: `{ id: '<instance>:wake', kind: 'wake', anchor: <now>, dueAt, onDue: 'wake' }`, with one wake per
  instance, upserted when it changes and cancelled when it is no longer needed.
- Human task: `onTimeout: 'timeout'`. The answer is read from `payload.answer.decision` (or `payload.decision`), and
  the task id from `payload.taskId` (or `humanTaskId`, `task.id`, `id`).
- Migration payload: walked structurally for incident, SLA, escalation and notification rows and event objects, and
  merged with `sor/<instance>.json`.

## Known limits

- If a round-3 event at an instant changes an outcome whose records round 1 already committed (for example a pause at
  t, then a stop at t), the committed record stays.
- A late event (`at` < now) is placed at its own time in the replay, but committed records are not undone.
- The second incident of the S8 tie can be found by later inbound messages only through the owner tag on its
  assignment notice.
