**P1-1. Strict acceptance: one shared boilerplate quote, or a JSON-syntax fragment, "explains" every diff case.**
- **Where:** `experiments/jit/acceptance.mjs:83-97` (`taskTexts`, `quoteOccurs`) and `:100-104` (`explainCase`).
- **Cause:** every records task has the same opening sentence in its prompt. A quote only needs to be a 12-character substring of the prompt, of `JSON.stringify(inputs)` or of a string value, and one note block can name every case.
- **Reproduction 1 (`a1.mjs`):** real records dev tasks (seeds 201-210), 1 exact trace and 9 diffs at partial 0.3. BUILD-NOTES is the single line `trace-1 trace-2 … trace-9: the task says "You are migrating customer and supplier records".` Result: `accepted true`, passed `[clean, agreement, explained]`, mean partial 0.37. The agreement criterion passes through its "one exact trace" branch.
- **Reproduction 2 (`a2.mjs`):** the note `trace-0\n> "documents": [` verifies against a kinetics task, because it is a fragment of the serialised inputs JSON.
- **Minimal fix:**
  - Take quotes only from the prompt and from string values in the inputs, not from the serialised JSON text.
  - Reject a quote that also appears in every other case's task. Common boilerplate then never counts.
  - Require each quote to explain a single case, or require different quotes for different cases.
  - Add a minimum word count, e.g. at least 3 words with letters.

**P1-2. The relative tolerance also applies to integer ids and money amounts.**
- **Where:** `experiments/jit/compare.mjs:41-46` (`numbersEqual`).
- **Effect:** in records, `entity_id` 150 equals 151, `source_rows` [100,150] equals [101,151], and `amount_usd` 1000 equals 1009.9.
- **Reproduction (`m2.mjs`):** `tolerantEqual` and `stream.sameAnswer(…, 'tolerant', {relTol: 0.01})` both return `true` for `{records:[{entity_id:151, source_rows:[101,151], given_name:'Ana', amount_usd:1009.9}]}` against `{…150, [100,150], 'Ana', 1000}`.
- **Consequence:** in a records arm with tolerance on, a wrong merge becomes "exact" in shadows, adjudication, the host check and the strict rule's "one exact trace" branch. Those wrong merges are the very under-merging misses DEV-NOTES describes.
- **Minimal fix:**
  - Compare exactly when both numbers are integers (`Number.isInteger(a) && Number.isInteger(b)`).
  - Or take the tolerance from the output schema: exact for `type: integer`, tolerant only for listed number paths such as kinetics `vmax` and `km`.

**P2-1. The solver can replace `tools/compare.mjs` before the host check loads it.**

**P2-2. Above 200 items, partial agreement scores lower than canonical, and a code comment claims a greedy step that isn't there.**
- **Where:** `experiments/jit/compare.mjs:220-232`. The comments at `:24-25` and `:224` say this path uses check-traces' greedy pairing by overlap. It actually pairs key-equal items, then pairs the rest by position.

**P2-3. `jit.compare 'tolerant'` with a canonical host check is accepted, and it makes the host check fail its regression cases.**

Under the canonical host check, a recompiled solver must match them exactly, but `compare({vmax:4.0198},{vmax:4.0213}).exact` is false. `clean` then requires every regression exact, so every later compile is unclean.

**P2-4. The size cap is per array level, not per whole comparison.**

## Findings

**P1-1: no upper bound on relTol/absTol, so shadows can be made to always agree.**
- **Where:** `experiments/jit/compare.mjs:32`; it reaches the stream config through `experiments/jit/stream.mjs:78` and `:88`.
- **Problem:** `tolerance()` only requires a finite number ≥ 0.
  - `normalizeConfig({jit:{compare:'tolerant', relTol:2}})` is accepted, and then `tolerantEqual({vmax:4,km:1},{vmax:-1000,km:1e6},{relTol:2})` returns true.
  - With absTol 1e9, `1` equals `5e8`.
  - With relTol 0.1, which is the oracle's own tolerance, km 100 equals 110. So a correct answer would agree with the bed's `near-miss:km-12pct` control, and with trap answers 8–13% away.
  - `check-traces --rel-tol 5` is also accepted.
- **Repro:** `rv21/t1.mjs`.
- **Fix:** reject relTol > 0.05, and require absTol to be small (or 0 for ids/cents), unless an explicit `allowLooseTolerance: true` is set and recorded in the arm def. Apply the same check in `check-traces.mjs` `comparisonOf`.

**P1-2: tolerance is applied to integer ids and money, which is wrong for records.**
- **Where:** `experiments/jit/compare.mjs:41-45`.
- **Problem:** every number gets relTol, including records' `entity_id`, `source_rows` (row ids) and `amount_usd`. The README grades amounts "to the cent" and ids by integer equality.
- **Repro:** at the defaults, `sameAnswer({records:[{entity_id:1321,source_rows:[1321,8546],amount_usd:67833.59}]}, {records:[{entity_id:1330,source_rows:[1330,8600],amount_usd:68400}]}, 'tolerant')` is true. Under 'unordered' it is false.
- **Fix (minimal):** in `numbersEqual`, compare two integers exactly. Better: add an optional `tolerantKeys` allowlist (e.g. `['vmax','km']`) and compare every other number exactly.

**P1-3: strict acceptance's "explained" rule is passed by boilerplate shared by every task.**
- **Where:** `experiments/jit/acceptance.mjs:91-96` and `:100-104`.
- **Problem:** a quote only has to occur somewhere in the case's own task. The family prompt is identical across seeds (records: identical; kinetics: mostly shared), so one note covers every diff case. For example, `- trace-1, trace-2: the agent is wrong; "You are migrating customer and supplier records from 6 legacy systems…"` explains both cases.
- **Effect:** `judgeAcceptance` strict then accepts at trace mean partial 0.467, because one exact trace satisfies the agreement criterion. This is what D4 was meant to stop, and it contradicts prompt v3's own "a sentence from another case does not count" (`prompts.mjs:95`).
- **Repro:** `rv21/t2.mjs`, which uses real dev-seed tasks from both beds.
- **Fix:** accept a quote only if it does not occur in every other case's task (or not in the shared `prompt.md`), and record that in the result. Optionally require at least one quote per case.

**P2-1: strict acceptance is allowed with prompt v1/v2, which never ask for double quotes.**
- **Where:** `experiments/jit/stream.mjs:91`, `experiments/jit/compile.mjs:172`, `experiments/jit/acceptance.mjs:73`.
- **Problem:** `normalizeConfig({compile:{acceptance:'strict'}})` is accepted with no promptVersion. The v1/v2 finish text only says "quote the task sentence", but only double, curly, «» or `>` quotes are recognised.
- **Repro:** `explainCase` returns false for a verbatim sentence in backticks or single quotes, and true for the same sentence in double quotes (`rv21/t3.mjs`).
- **Fix:** refuse `acceptance:'strict'` unless `promptVersion >= 3`, or also accept backtick and single-quote spans.

**P2-2: no order-insensitive exact mode for compile, and v3's tolerance sentence is wrong at 0/0.**
- **Where:** `experiments/jit/compile.mjs` `COMPARE_MODES`; `experiments/jit/prompts.mjs:87`.
- **Problem:** canonical check-traces marks an order-only difference as "diff" with partial 100%. Under strict acceptance such a case can't be legitimately explained: a judge on `{status:'diff', partial:1}` fails 'explained'.
- **Workaround that works today:** `compare:'tolerant', relTol:0, absTol:0`. Permuted records are then equal and 1000 ≠ 1001.
- **Remaining problem:** at 0/0, prompt v3 still tells the builder that "a fitted number need not match the agent's to the last digit".
- **Fix:** add `compile.compare 'unordered'` (tolerant at 0/0), or leave the tolerance sentence out when relTol and absTol are both 0.

**P2-3: the complexity note understates the cost of nested arrays.**
- **Where:** `experiments/jit/compare.mjs:17-25`, `:221`.
- **Problem:** the cap is per array, but the weight matrix makes a recursive call for every pair, so nested costs multiply. The comparison runs in the check-traces parent process, outside the per-case timeout.
- **Measured:** 40×40 nested arrays of near-equal numbers take 0.6 s; 80×80 take 12.2 s. 200×200, which is still inside `MATCH_CAP`, would take far longer, bounded only by the 30-minute host-check timeout. Real outputs are small (records ≤ about 78 records with short `source_rows`), so live configs are not affected.
- **Fix:** cap total `cmp` calls per top-level comparison and fall back to greedy past the cap, counting it in `approx`. Correct the stated bounds.

## Recommended defaults (from the bed READMEs; no oracle code read)

**records:** keep `jit.compare 'unordered'` (exact), as in both live configs.
- Reasoning: every number in the answer is an integer id or a cent amount fixed by the spec (half-away-from-zero rounding, `|Δ·100| < 0.001`). Sign flips and FX tables are per-task traps. Two correct solvers therefore agree exactly, up to order.
- If strict acceptance is used for records, set compile to `compare 'tolerant', relTol 0, absTol 0` (or 1e-6 for float noise). Never use relTol > 0 here, because of P1-2.

**kinetics:** `jit.compare 'tolerant'`, relTol 0.01–0.02, absTol 1e-9, hard cap 0.05. My reasoning (inference from the README, not measured):
- Two NLLS fits of the same cleaned data differ by noise. The DEV-NOTES example, 4.0213 vs 4.0198, is 0.04%.
- A fit on replicate means can sit up to 8% from the truth; the reference NLLS is within 5%.
- Trap answers miss the truth by more than 13%, so they sit at least 8% from a reference-quality correct answer. The near-miss control is a single Km 12% high.
- So 0.01–0.02 covers differences between fitting methods with a 4–8× margin below the smallest trap separation. Anything from about 0.07 upward lets the bed's own near-miss control agree with a correct answer.
