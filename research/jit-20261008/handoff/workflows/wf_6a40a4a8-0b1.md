## API
**`profile.mjs`**
- `learnProfile(tasks)` takes task.json objects or trace records that carry `.task`.
- `checkProfile(profile, task, {ignore})` returns `{novel, score, reasons, near, n}`, with no model call. `reasons` and `near` name the feature, the path, the ratio and examples.
- `widenProfile(profile, task)` returns a new profile and leaves the old one unchanged.
- Helpers: `SIZE_FEATURES`, `PARAMS`, `describeProfile`, `goodTuring`, `rateThreshold`, `shapeOf`, `classOf`, `lineShape`/`lineSig`, `promptSentences`.
- A profile is plain JSON with sorted keys; it is deterministic and the same whatever order tasks are merged in.

What it checks, all generic (no family-specific code):
- **Shape:** which paths exist and their types, including new and missing paths.
- **Numbers:** range with a margin of `max(0.5·span, 0.25·|max|)`, and whether values are whole numbers.
- **Sizes:** array lengths, string lengths and line counts, each with a margin.
- **Short strings:** enum values; the format class (date, phone, id, …) and shape signature on format fields. Name-like free text is checked only by type and enum.
- **Multi-line text:** a set of line families (leading word, delimiter, field count) and finer line formats.
- **Prose:** vocabulary of lower-case words (capitalised words are treated as names and left out).
- **Prompt:** sentence skeletons with numbers, quoted text and the task's own input values masked.

Each set feature's threshold adapts to how much that field normally changes between tasks: `clamp(2·GT + 0.02, 0.05, 0.5)`, where GT is the Good-Turing estimate of how often a new item appears.

**`durability.mjs`**
- `computeDurability(rows, events, {window: 6, minSuccess: 0.8})` reports per arm: version churn (spans, changes, rows between changes), deopt and guard-fire rates, silent misses (oracle view), overruled answers, shadow disagreement and $/task, each as totals and over a sliding window.
- **Time-to-durable:** the first row p at which one version runs rows p..p+W−1 and at least S of those rows were delivered by compiled code and passed. It is reported in two views: the oracle view, and the system view ("compiled ok with no shadow disagreement" instead of the oracle's pass). Each view gives episodes, `confirmedIdx`, `usdToConfirm`, `holdsToEnd` and relapses, or `null` with "never durable".
- **CLI:** `node experiments/jit/durability.mjs <runDir> [--window N] [--min-success S] [--series] [--json]`.

**`eval-profiles.mjs`**
- `node experiments/jit/eval-profiles.mjs <runDir> [--nversion research/jit-20261008/nversion-records-dev.json]`.
- It regenerates each row's task (dev split only, checked against the row's task hash), then replays the stream under three policies: `frozen`, `interp` and `version`. Each runs with and without the size checks.

## What we're missing
1. **Detecting meaning drift.** Shape checks are cheap but blind to the drift that actually broke solvers. The next lever is to profile the solver's own intermediate values: judge answers per name, branch counts, field counts at each `flow.step`, recorded in `trace.jsonl`. That is real type feedback, but it needs a `flow.mjs` hook, which is off-limits to this workflow.
2. **The profile belongs to the solver version, not the stream.** It should be stored with each version, replayed by the D9 refusal-preservation check (task #41), and given to the router so a novel task is interpreted or shadowed.
3. **Stopping rules.** The system-view durability could become an oracle-free rule: lower the shadow rate once durable, raise it on a relapse. Held-out streams should report the gap between the system and oracle views as the silent-failure measure.
4. **Not yet wired in or validated.** Neither the profile nor durability is wired into `stream.mjs` or `report.mjs` (both are being edited elsewhere). The thresholds were tuned on these same dev streams, so they need a preregistered held-out check before any claim.

**Conclusion**
1. In both families, the drift-segment detection is real but rests on size; in records it is size only (0/8 without size checks). The records drift changes meaning (a new status value, a swapped date order), and shape checks cannot see that.
2. D9 in the N-version probe: v2's own profile would have refused all 6 of its wrong d4 answers and 0 of its d3 answers. It amounts to a "this is bigger than my training inputs" detector.
3. The live D9 catch at #16 was luck: shadows run every 4th task and 16 is a multiple of 4. A version profile flags #16 every time.
4. The d3 misses (D1 under-merging) make up 4 of Opus's 6 silent misses and 0 of them are flagged. No input check can catch those; only shadows, invariants and ensembles can.
5. The static solver is where the profile pays: 6 of 7 silent misses caught for 2 false alarms, a net +4 expected passes for $1.55.
6. For the JIT arms the trade is poor. Opus pays $4.66 to re-route 5 correct answers and gains 2; Sonnet pays $2.21 for nothing.
7. Profiles don't stay calibrated as they learn. On kinetics, learning from more normal tasks raised false alarms from 2/13 to 7/13. Fields like enzyme name get locked into a closed list after about 10 tasks, the prompt check tightens, and each feature can flag on its own with no overall false-alarm budget.
8. One drifted example in a compile pool makes the whole drift segment look familiar (Opus v3) while the solver still fails 2 of 7 d4 tasks. Ranges should widen only per confirmed input, not to the full span of the pool.
9. The system view thought Opus was durable 12 rows before the oracle did (task 6 vs 18), and the static solver "holds" to the end while the oracle sees it fail. That gap is the silent-failure measure to report on held-out runs.
10. The samples are tiny (8 d4 tasks, one compile lineage per arm) and the thresholds were tuned on these same streams. None of this is a claim yet; it needs a preregistered held-out check.

**What we're missing, measured against the full end-to-end vision**
- **The beds have no drift types.** Each drift segment is a difficulty step that is bigger by construction, so recall based on size can't be falsified. Held-out streams need three kinds of segment: bigger input with the same meaning (should not deopt), same shape with new meaning (the records case), and a changed format.
- **Missed answers have no price.** $/task treats a silent miss as free, so no routing rule can be cost-optimal. The objective should be the lowest $ subject to an upper bound on silent misses, with interpreter time spent where it buys the most.
- **Shadows run on a fixed every-4th schedule.** Random (seeded) shadows, more likely on novel inputs, with inverse-probability weighting, would give an unbiased silent-miss estimate from the shadows alone. That would turn the system view into a stopping rule that needs no oracle.
- **We profile inputs; a real JIT profiles types.** It records the values the compiled code sees at each step (judge answers, branch counts, field counts) and compares them with the outputs. Profiling the outputs (for example predicted entities per input row) can be done now from `results.jsonl`, with no `flow.mjs` hook.
- **One calibrated score instead of hard per-feature flags.** One option is a leave-one-out score over the tasks the version was confirmed on, with a target false-alarm rate. Store it with the solver version, make the refusal-preservation check (task #41) forbid widening it, and let the router use it.
- **Wiring is blocked.** Hooking this into `stream.mjs`, `report.mjs` and `flow.mjs` waits for the other workflow; held-out work needs at least 2 compile lineages per arm.

## Review findings

**P1-1, fixed in profile.mjs: size leaked through the "no size checks" ablation.**
- The kinetics d5 signals called non-size earlier were new document ids D13–D15 and condition C8. d5 has 15 documents where d4 has 12, and 8 conditions where d4 has 7, so those ids are counters.
- New feature `enum-ordinal`: an unseen value that continues a numbered series the enum already holds (two or more members). It is now in `SIZE_FEATURES`.
- Kinetics without size, profile from the first 3 tasks: the d5 flags drop from 8/8 to 2/8. The normal segment flags 2/13, so that is chance.

**P1-2, fixed in durability.mjs: the system view of time-to-durable could be gamed by not checking.**
- A solver that is never shadowed was "durable" by construction. The static solver's "holds to end" came from this.
- That would also make the proposed stopping rule ("lower the shadow rate once durable") confirm itself.
- The system view now needs at least `minShadows` (default 1) answered shadows in each window, and at least 80% of them must agree.
- The old definition is kept as `systemUnchecked`. There is a new `--min-shadows` flag.

**P1-3, done in eval-profiles.mjs: thresholds were tuned on the same streams they were scored on.**
- New `--tune <otherRunDir>` mode. It picks parameters on the other family's task stream, using only the difficulty segments (no oracle), from a 729-point grid. It then replays this run with the chosen parameters.
- The score J is the drift flag rate minus the normal flag rate, averaged over the "never widened" and "widened with normal tasks" policies.

**P2, fixed:**
- **Missing rows:** a task index missing from the rows was skipped, which let a window jump over it. It now breaks the window, and `missingRows` counts these.
- **Counterfactual cost:** it only reported gross interpreter cost. It now also reports the net cost (minus the compiled, shadow and adjudicator cost a re-route avoids) and a paired reading (the actual cost and pass of the same task in the interpreter model's agent arm).

**P2, not fixed (fixing them would mean more tuning on the same data):**
- **Enum lock-in from tiny pools.** Kinetics Opus v2 was compiled from 5 tasks; 4 of them had "NADH-dependent reductase". That made the enzyme class an enum, so tasks #10–15 are all flagged on `enum@inputs.study.enzyme_class`. The earlier "1/1 silent miss caught" for kinetics Opus is this flag, with precision 1/6, which is the base rate. The right fix is the calibrated score already on the list.
- **Design fitted to records.** The delimiter list matches the records dialects one for one (` :: ` ATLAS, `;` LEDGR, ` — ` Vendex, ` | ` BRIGHTDESK/KOBO). No code names a family, but these choices can only be tested on a third family nobody has looked at.
- **Recompiles not modelled.** In a live JIT a re-route is a deopt, so two of them trigger a recompile ($0.4–$8 on these runs). The JIT counterfactual costs are therefore lower bounds.

**Checked and clean:**
- **No oracle leakage.** The profile reads only `prompt`, `inputs` and `files`; task id, seed and difficulty are dropped, and numbers in the prompt are masked ("holds 85 rows").
- **Policies:** the per-version policy uses only fields the system sees (`stateAfter`, shadow agreement). The "widened with all normal tasks" policy reads difficulty labels and is marked as a reference only.
- **No peeking:** each task is checked before any widening, and N-version pool tasks are left out of the counts.
- **Version pools** match the `compile.json` trace ids for kinetics; records pools have at most 8 traces (the `maxTraces` limit).

**Hand-recomputed samples (all match):**
- **Opus records, oracle durability:** window 18–23 is 5/6, giving durable from 18, confirmed at 23, $7.53. Every earlier v2/v3 window is at most 4/6.

## Final conclusion

1. An input profile is a size detector on these beds. In records, all 8 drift flags are line count or string length, and without size checks nothing is flagged for any parameter choice from the other family. In kinetics, the content signal (new document kinds) is real but near the threshold.
2. It pays only for the static solver: about +4 expected passes for about $1.10 net. For the JIT arms, the per-version profile sees nothing, and the "first 3 tasks" profile re-routes correct answers at or below base-rate precision.
3. The D9 result stands, and it is a "bigger than my compile pool" detector. A single drifted task in a pool erases it.
4. The cross-family split shows that drift recall does not depend on the parameters. The normal-segment false alarms do: under widening, 7/13 with the transferred parameters against 4/13 in-sample. False alarms grow as profiles learn.
5. With shadows required, the system view still calls Opus durable 12 tasks before the oracle does. Its v2 silent misses (#7, #11, #13) fell between the scheduled shadows on #8 and #12.
6. None of this is a claim. It needs a preregistered held-out run with these parameters, W, S and `minShadows` frozen, plus a third family.

## What we're missing, against the full end-to-end vision

- **The guard is on the wrong layer.** A VM's guard checks the exact assumption the compiled code relied on. Ours checks input size, which the compiler never relied on. Meanwhile it misses what the compiled code does assume: the per-task conventions read by the `rules` judge (D11) and the fuzzy-merge threshold (D1). The records bed draws its conventions per task even at d3, so a stream-level novelty check cannot see them by design. The fix is an assumptions manifest written at compile time: every `flow.judge`, branch and threshold, with the task sentence it was read from (an extension of the D4 quoting rule). At run time, profile the values at those points and check agreement across several samples, with the profile stored per version and kept intact through recompiles (task #41). This needs a `flow.mjs` hook, which is blocked by the other workflow.
- **A $0 routing simulator.** Agent arms ran every task, and the N-version probe ran every solver on every task, so we have a full task × solver/agent matrix. Replaying the stream state machine over it (deopts, recompile triggers, shadows) would score any routing policy end to end offline: the profile, N-version disagreement, random shadows. That replaces the per-row counterfactual, which ignores recompiles.
- **Oracle-free stopping rules.**
  - **Random shadows:** seeded random shadows, with inverse-probability weighting and more weight on novel inputs, would replace the every-4th schedule.
  - **Sequential test:** a sequential test on the miss rate (an upper confidence bound or SPRT), instead of the 80%-of-6 window, would give an oracle-free durability claim.
  - **Objective:** report "lowest $ with silent misses below a bound".
- **One calibrated novelty score.** A leave-one-out (conformal) p-value over each version's confirmed inputs would bound the false-alarm rate and fix the enum lock-in and the growing false alarms in one place.
- **Beds need drift types.** The drift segments need three types: bigger with the same meaning, same shape with new meaning, and a changed format. Otherwise every detector is a size detector.
- **Blockers:**
  - wiring into `stream.mjs`, `report.mjs` and `flow.mjs` waits for the other workflow;
  - the preregistration has TBD fields that must include these parameters;
  - the held-out round needs at least 2 compile lineages per arm and a third, unseen family.
