**Findings:**

- **How swarms work.** Every system surveyed uses the same primitive: spawn a worker with a fresh context and get a condensed result back. They arrange it four ways:
  - one orchestrator fanning out to workers (Kimi, Anthropic's research system, Claude Code, LangGraph `Send`);
  - handing control and history to another agent (OpenAI Swarm and Agents SDK, AutoGen, `langgraph-swarm`);
  - a shared board or message pool (MetaGPT, LbMAS, Claude Code agent teams);
  - a learned or optimized topology (Kimi's trained orchestrator PARL, GPTSwarm, MaAS, MASS, Puppeteer, FlowReasoner).

  For Kimi I read the primary source, the K2.5 technical report (2602.02276v2): its reward terms, the two failure modes it names (the model never parallelizing, or spawning useless agents), its critical-steps latency metric, the tools, the step limits and the Table 6 results.
- **When swarms pay off.** Only on breadth tasks: Kimi gains +17.8 points on BrowseComp and +6.3 on WideSearch and runs 3–4.5× faster; Anthropic reports +90.2% on an internal eval. On sequential or coding work they are neutral or negative, and they cost about 15× the tokens of a chat. The README's usage-limit incident is the repo's own measured cost.
- **Claude Code dynamic workflows.** §1.4 documents the mechanics R02 did not record:
  - Script and resume: the full script API, how resume replays the journal in start order, and that `workflow()` nests only one level.
  - Limits: the concurrency, item and agent caps, the prompt-cache stagger, and the rule that script-computed prompts never count as consent.
  - Ultracode: what turning it on changes.
  - Subagents: they nest 3 layers deep, 20 can run at once, and they can be isolated in a worktree.
  - Agent teams: a shared task list with file-locked claiming, JSON mailboxes, and no nested teams.
- **Mapping to Foundry.** §2 has a 24-row table with file and line references. Fan-out, typed outputs, journaled resume and caps are the same in both. Foundry differs in typed control fixed before untrusted data, narrow judgments, independence labels and a model class per node. Swarm workers fit into Foundry as `executor` nodes.
- **The 94% coverage figure says nothing about agent workflows.** The 1,342-item corpus behind it contains no agent-orchestration framework: no LangGraph, CrewAI, AutoGen, OpenAI Agents SDK, Claude Code workflows or swarms. Lane 1 found the same gap.
- **Scope decision.** A swarm belongs in scope as an operator over the existing IR, not as a subsystem: plan → partition check in code → bounded `map` of typed workers → code reducer → independent `verify`. This composes from today's node kinds, and nothing in ROADMAP §3 needs to change. Seven small additions are listed in §3.3, along with what to exclude and why.
- **Policies.** §3.4 says nodes never spawn subagents, except `executor` nodes under limits set from outside. §3.5 gives the three-tier information design: private notes, typed results along edges, and a typed run board. §3.6 gives the rules for nesting, recursion and iteration.
- **Frontier research and open source.** Use them for semantics and baselines, not as dependencies. Restate's licence is BSL 1.1 and Inngest's is SSPL, so avoid both as dependencies. LMQL has had no release since 2023-10-14, and AutoGen is in maintenance mode.
- **What changed in 2026.** Small trained orchestrators now beat much larger general models: ToolOrchestra-8B, the AgentFlow 7B planner, WideSeek-R1-4B. Weaver distils an ensemble of weak verifiers into a 400M model that keeps about 98% of its accuracy, which is the most direct route to a useful Kev verifier. Haiku 5.5 as constructor therefore stays a hypothesis for C0 to test, and Kev is the model to train.

## Agent result 2

I've written the lane 7 review: `/home/user/workflow-foundry/research/review-20261007/07-context-subagents-audit.md` (866 lines). The only file I changed is that one. Three read-only probes ran from a scratch directory outside the repo against current HEAD (`fd7bd27`); none was committed.

**Recommendations**
- **Shared board:** yes, but for typed facts with provenance, not a free-text chat. It is scoped to one run, and nodes write to it only through their validated outputs. Each read is capped and its receipt records exactly what the node saw. It ships only if it beats the same workflow without a board by at least 15% per dollar on a game or grid exploration bed. Otherwise it is dropped.
- **Private notes:** each node gets its own scratch space. Loops can keep their own notes across iterations. A note reaches other nodes only through a typed output field.
- **No shared store that persists across runs:** this disagrees with ROADMAP §2.2 and the lane 1 review.
  - Lessons from earlier runs become either a replay-proven change to the next workflow version or an AMP memory claim. Otherwise Foundry becomes a second memory store, which AMP's single-writer rule forbids.
  - Workflows that keep their own data between runs (a cursor, a chat session) use a separate typed state tool. The corpus coverage report puts that construct in 10% of the 1,342 workflows, and says adding it makes 30 more expressible.
- **Subagents inside nodes:** you are not overcomplicating it, provided there is exactly one bounded kind, the `executor` node.
  - It has its own budget, reserved from the run's; a tool allowlist; a sandbox with no network by default; a typed result; a mandatory verify step after it; and a depth limit (2 by default, 3 at most).
  - Its transcript is hashed and stored as evidence, never passed to other nodes as context.
  - A Foundry-built agent loop stays deferred until an executor is measured and found insufficient.

**Findings, with evidence**
1. **Store cost grows quadratically (measured).** Every event rewrites the whole run record: 3.8 ms per event at 100 events, 142 ms at 4,000. A 4,000-event run spends about 7 minutes just writing state. The 10 MB state limit stops a run at about 5,000 such events. A Rust port with the same write pattern would have the same curve; the fix is per-node rows.
2. **Prompt caching mostly costs money on the `claude -p` route (measured, cause inferred).**
   - About 80% of input tokens are written to the cache and rarely read back.
   - Recomputing the logged costs reproduces the totals to $0.0001 in two independent logs, but only if cache writes are billed at 2× (the one-hour price).
   - Disabling caching would have saved an estimated 14% of spend (Haiku 5.5 log) and 19% (Sonnet 5.5 log).
   - For Haiku 5.5 nodes, output tokens are about 65% of cost, averaging 4.2K per call, so short typed outputs matter more than caching.
3. **A security check is missing (measured).** An effect whose firing is decided by untrusted data passes validation. The probe used a `when` condition on an untrusted value to gate a file write; it validated. ROADMAP §2.9 specifies the check that should catch this, and it isn't implemented.
4. **Executors can likely leak data (inferred from code, untested).** The executor sandbox has no network isolation and allows Bash. The CLI's login directory stays readable inside the sandbox. A nested `claude` call inside an executor would bypass every cost ledger and is caught only by an after-the-fact transcript scan.
5. **Audit records can be edited undetected.** Model responses, decision records and executor transcripts are not bound into the run's hash chain. Nothing anchors the chain head outside the database file.

The document also covers worst-case security scenarios (injection through the board, laundering data through many small "safe" outputs, confused deputy), a per-run "flight recorder" view, and a six-stage plan with tests and kill criteria.

**Decisions for you**
- **Executor model access through a host gateway.** This probably needs an API key you provide via environment variable. It closes findings 4 and the nested-spend gap. Approve it before any executor reads untrusted third-party content.
- **No shared store across runs.** This amends ROADMAP §2.2.
- **A free test turning prompt caching off** for single-shot CLI nodes. Check first that the `DISABLE_PROMPT_CACHING` variable exists in the pinned Claude Code version; I'm recalling that name, not confirming it.
