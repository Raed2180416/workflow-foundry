## Agent result 2

I've written the lane-2 review to `/home/user/workflow-foundry/research/review-20261007/02-ir-expressiveness.md`. Nothing was committed, and no other file in the repo was touched.

**Coverage (the doc's main correction):**
- **The "94 %" in COVERAGE.md is really 93.74 %** (1,258 of 1,342 items). Reaching ≥ 94.0 % needs 1,262 items.
- **That number is "declared" coverage.** It compares converter labels against a list of constructs; nothing is compiled or run. The coverage script also never reads which constructs are actually implemented, so re-running it after each stage would keep printing 35 %. The doc proposes a construct ledger plus two more numbers: "compiled" (every item turned into Foundry IR and passed by the real validator) and "executed" (items with oracles run against mocks).
- **Nine constructs are each individually required for 94 % declared:** schedule, webhook and event triggers, error branches, completion hooks, adaptive retry, `call`, cross-run state and agent tool loops. The cheapest set that gets over the line reaches 94.26 %, only 3 items of margin. Since compiled coverage will come in lower, a measured 94 % realistically needs all 19 constructs (declared ceiling 99.85 %; 2 dashboard items stay unsupported).

**What the doc contains:**
- **Per-construct specs (19):** for each construct, corpus evidence, semantics, IR syntax, runtime rules (durability/replay, budgets, cancellation, idempotency, labels/authority), static checks, tests and effort.
- **Additions the corpus doesn't count but which are needed:**
  - a workflow output contract;
  - a pure expression language;
  - finer label rules, plus taint from `when` branches;
  - `detach`/`await`;
  - sagas;
  - queries and updates;
  - heartbeats and cancellation;
  - shared rate limits;
  - a written semantics spec with a conformance suite.
- **Composition section:** covers every edge case the task listed. Recursion by hash is impossible (a document can't contain its own hash), so recursion is only allowed through local flows or `self`, with a declared depth limit.
- **What must not be allowed:** 13 rules.
- **Scope:** a per-item argument against ROADMAP §3, recommending two wording amendments (THESIS §4 and AGENTS.md's "no resident workers").

**Measured on the current runtime and corpus:**

| What | Result |
|---|---|
| Engine overhead, 500-node chain of trivial tasks | 21.1 s, 42 ms per node (100 nodes: 1.1 s), so it grows faster than linearly |
| Where that time goes | 33 % per-step SQLite transaction, 19 % re-reading the whole run record, ~25 % re-validating it |

All of these slowdowns are fixable in JavaScript; none argues for a Rust port.

**Plan:** stages S0–S7. Declared coverage first clears 94 % at S6 (1,304 items, 97.17 %). Every stage ends with declared, compiled and executed numbers, a per-platform table, and a capability number (Haiku 5.5 builder with versus without the new constructs). I recommend stopping after S2 to check capability before committing to the rest. Total effort is about 125–190 engineer-days; that figure is my estimate, not measured.

**Decisions for you:**
- **Resuming runs after an engine change.** Today any engine source edit or Node upgrade blocks every paused run from resuming. That makes long waits, schedules and chat sessions unusable during development. I recommend allowing resume when replaying the run's event log reproduces its saved state.
- **What "94 %" means.** I recommend compiled coverage on a fresh held-out sample, not declared coverage on this development corpus.
- **Who activates triggers.** I recommend owner approval per trigger, tied to the workflow's hash; model-built workflows can declare triggers but never switch them on.
- **Stop after S2 or run straight to S6.** I recommend stopping after S2.
- **Add ~100 agent-framework workflows first.** The corpus has none (LangGraph, CrewAI, Claude Code workflows, swarms), so I recommend adding them before any "any workflow" claim.
