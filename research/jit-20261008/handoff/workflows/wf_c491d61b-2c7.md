### Deviations from the spec (all recorded in `PROTOCOL.md` §8)
- **Upload hash header:** added an `x-bridge-body-sha256` header, required for `PUT /files`. Without it, a 256 MiB unauthenticated upload would hit the disk before the signature could be checked. The canonical string is unchanged.
- **Uploads:** `PUT` is allowed into `data/` and `runs/` only. `logs/` holds the daemon's own logs, so the cloud could otherwise rewrite the evidence.
- **`maxState`:** 384–8192, not 64–8192, because `kev.train` refuses anything below 384.
- **Python:** 3.12 (3.13 also works), because Kev requires `>=3.12,<3.14`.
- **Non-fast-forward handling:** fetch, reset to the remote tip, reapply, commit and push, with backoff. This replaces `pull --rebase`; the result is the same and it works in shallow clones. It never force-pushes.
- **Commit signing:** laptop mailbox commits are unsigned (`commit.gpgsign=false`), so a passphrase prompt cannot hang the background service.
- **Services and the GPU queue:** services are not queued behind training. They share VRAM with training jobs, so on 8 GB stop them before a large run.
- **llama `hf` models:** come from the operator's allowlist without a revision pin, because llama-server cannot pin one. For a pinned run, download and hash-check the file into `data/` and use the `gguf` parameter.
- **Additions not in the spec:**
  - `/ping`, `GET /jobs`, and `/jobs/<id>/stop` as an alias for cancel;
  - CLI `ls`, `jobs`, `req` and `get --dir`;
  - `daemon --check`;
  - keys are refused after 24 h without a successful refresh;
  - the daemon publishes `state:"stopped"` on shutdown;
  - the client corrects clock skew from the `Date` header;
  - a pinned `kev-requirements.txt` exported from Kev's `uv.lock` with sha256 hashes (it resolves offline with `--require-hashes`).

## What held (59/59 rejections)

Signature core is sound: alg-confusion / key-id spoofing → `bad_signature`; path/method/body tamper → `bad_signature` / `body_hash_mismatch`; stripped/empty/garbage/wrong-length/valid-shape-wrong sigs → refused; duplicate `x-bridge-key` (Node comma-joins → `unknown_key`); mixed-case header names correctly honored (200, no bypass); replay within a live daemon blocked by the nonce cache; nonce consumed only *after* the signature verifies (no nonce-burning). Timestamps: seconds-not-ms and ±10 min → `stale_timestamp`; negative/NaN → `bad_timestamp`. Nonce: short/non-hex/uppercase → `bad_nonce`. **Path traversal — every variant refused** before touching disk: `../`, `%2e%2e`, double-encoded `%252e`, `..%2f`, backslash, `%00`, absolute, `C:/`, unicode fullwidth `．．`, and `logs/../runs/../data`. **Flag/param injection — all refused** by schema: dataset `--out=/etc/cron.d/x` and `-rf` (NAME_RE forbids a leading `-`), dataset traversal, nonexistent/unstaged dataset, `base` outside `BASE_RE`, unknown `extra` flag, `extra.suite` traversal, `llama hf` / `kev.serve` hub id outside the allowlists, non-object params, extra top-level body fields. Proxy with no running service → 502 (no SSRF: upstream host/port come from the running service, never the request; `x-bridge-*`/auth/host/TE/CL stripped before forward). Oversize JSON (declared 5 MiB) → 413 pre-read. Uploads into `logs/` and dotfiles → refused. Upload without announced hash → `body_hash_required` (verify-before-write). Kev never sets `trust_remote_code`, so the transformers remote-code vector is absent.

## Blast radius of a malicious/leaked/prompt-injected cloud

**File writes and the registry are bounded** — uploads to `data/`+`runs/` only, reads within `data/runs/logs`, fixed job kinds, schema-checked params, argv arrays (no shell), operator-controlled binaries. **But code execution is not guaranteed bounded (F1):** a registry job deserializes an attacker-uploaded `head.pt` through an unsafe-by-API `torch.load`; today only torch's ≥2.6 `weights_only` default (which the daemon neither pins nor verifies) stands between that and RCE. Plus availability DoS (F3) and mailbox-publish wedge (F4) from an authenticated caller. So the honest answer to the task's question: **writes are sandboxed; execution authority is not — it leans entirely on the executor venv's unpickler, which is outside the bridge's control.** Close F1 and the "bounded to registry + workdir" claim becomes defensible.

Scratch directories and keys are removed; the verification scripts (no keys) remain in `/var/tmp/foundry-work/bridge-verify/`. I did not touch git state. The only `PEM` files left under `bridge-*` are cloudflared's own test fixtures in the earlier e2e clone.

**How the bridge works, for the owner**
1. Your laptop runs a small daemon that listens only on 127.0.0.1:8765, plus a Cloudflare quick tunnel that gives it a public `https://<random>.trycloudflare.com` address.
2. The cloud session cannot reach your laptop directly, so the daemon writes its current tunnel address into a private-repo branch (`foundry-bridge`), and the cloud reads it from there.
3. Every request must be signed with the cloud's Ed25519 private key, which never leaves the cloud. The laptop trusts only public keys listed on that branch and refuses unsigned, stale, replayed or tampered requests.
4. The cloud can upload datasets into one folder, start a fixed menu of jobs (self-test, Kev fine-tune, benchmark, serve, and optionally llama.cpp) with validated parameters, download results, and call a served model through the daemon.
5. It cannot run arbitrary commands, read other files, or upload checkpoints for Kev to load. Kev only loads runs the daemon trained itself, with torch's pickle protection forced on.
6. One GPU job runs at a time, at most 32 queue up, and uploads and new jobs stop when less than 2 GB of disk is free.
7. A typical fine-tune: the cloud uploads data, submits `kev.train`, polls, downloads `runs/<id>`, then optionally serves it and calls `/v1/systemone`.
8. Kill switch: `bash ~/workflow-foundry/bridge/laptop/run/stop.sh` stops it at once. `node bridge/cloud/init-mailbox.mjs --kill` from anywhere with repo write access stops it within 5 minutes, and `--revoke <keyid>` removes one key.
9. Limits: Cloudflare can read the traffic, the laptop must stay awake on AC power, and after a reboot the bridge comes back by itself only with systemd (plus a Windows logon task on WSL). Running jobs are lost then and the cloud resubmits them.
10. A local Claude Code agent sets it all up by following `LAPTOP-HANDOFF.md`. It tells you when the tunnel is up and when the cloud first connects, and the full round trip through the tunnel is still to be proven on your laptop.
