## Behaviour

- **Stop path.**
  - `Runtime.requestCancel` writes `cancelRequest` and a `cancel.requested` event in one compare-and-swap update. It is durable and idempotent.
  - The process that executes the run polls for it every 250 ms and when it takes ownership. It aborts model calls and sandboxes and writes the verdict itself.
  - The verdict is status `cancelled`, verdict `inconclusive`, code `CANCELLED`. The run is final and is never resumed.
  - A run executing in the canceller's own process is aborted at once.
- **Runs nothing executes.** Runs parked on a timer, a question or an approval, runs never started, and runs whose owner died (including after the abort, before the verdict) are closed by the canceller in one update (`Runtime.closeCancelled`). Nodes the dead owner left `running` are settled, and the seal clears wait timers so `tick` cannot restart the run.
- **Effects in flight.** A task whose capability has effects ends `uncertain`, as before, and is listed in `effectsUnknown`.
- **Reports.** Every report carries a `message` saying what stopped, what was left unanswered, and which effects are in doubt.
- **Finished runs.** Cancelling a succeeded, failed or cancelled run is a no-op: clear message, nothing written. An `uncertain` run is also a no-op.
- **Unresponsive owner.**
  - After `--grace` seconds (default 10), `cancel` reports `not-stopped`; `--force` kills the owner.
  - `stop-all` always kills it. It freezes the owner, SIGKILLs every process below it by process group, then the owner, and closes the run.
  - The owner is identified by the pid and start time recorded in its run.
  - It never signals itself, its ancestors, or their process groups. `escalationPlan` is unit-tested for this.
- **`stop-all` scope.**
  - It cancels every unfinished run, executing and parked; `--executing-only` leaves parked ones alone. `uncertain` runs are left as they are.
  - One run that cannot be closed (broken chain, or a journal outside the workspace without `--journal FILE`) is reported and does not stop the others.
- **Process-group tracking (my addition).** Sandboxes and model CLIs are recorded in a new `run_children` table while they run. If an owner is killed from outside (SIGKILL), its sandbox keeps running; `cancel`, `stop-all`, or `resume` now finds and stops it. I added this because stop-all with a process-group kill was part of the brief. Recorded groups are verified by leader pid plus start time before any kill.
- **Exit codes.** `cancel` and `stop-all`: 0 stopped or nothing to stop, 2 an effect of unknown outcome, 3 not stopped. `foundry run` and `resume` now exit 3 for a cancelled run.
- **Unplanned changes beyond the brief.**
  - A capability that ignores its abort signal is abandoned after `cancelGraceMs` (2 s). If it has effects, the node ends `uncertain`.
  - An execution can no longer take ownership of a run closed in the meantime.
- **HTTP.** `POST /api/runs/:id/cancel` is now durable and works across processes. It returns 200 for a no-op or an immediate close, 202 when the owner was asked and the request is still pending. `POST /api/stop-all` is new. Neither kills anything over HTTP.

- `foundry trial` runs use isolated stores and are not reached by cancel or stop-all.
- Processes spawned by a capability itself are not recorded; only sandboxes and `process.mjs` children are.
- Cancelling an `uncertain` run is deliberately a no-op; there is still no reconcile command.
- The kill escalation needs Linux `/proc`.
- There is no UI "Stop all" button and no MCP cancel tool; the MCP omission is deliberate, to keep cancel out of model-facing authority.
- stop-all is terminal. There is no pause-and-resume stop; Ctrl-C and SIGTERM remain the resumable interruption. A cancelled run keeps its `input` in the store (`foundry inspect RUN`), so it can be re-run.
- An owner SIGKILLed while its sandbox is still in setup takes the sandbox with it (SIGPIPE). Only after the sandbox reports ready does the group survive its owner.

## The P1 (fixed)

**Cancel racing a pause.** The owner checks for a cancel request every 250 ms. If a request landed between checks while the run was about to pause (on a question, a timer or an approval), the owner parked the run without seeing it. The UI's cancel and `--grace 0` had already returned "requested" and stopped waiting. Nothing ever carried the request out, and a parked run's wait timer survived.
- In a randomized probe on the old code, 16 of the 20 zero-grace cancels ended this way. After the fix it was 0 of 60.
- **Fix** (`execute()` in `src/runtime.mjs`): in the same update that would park the run, the owner now closes it as cancelled if a request stands. A run that finished first keeps its result.

## Smaller defects (P2/P3, fixed)

2. **Answers and approvals after a cancel.** `answer` and `approve` were still accepted on a run with a standing request, though the docs said they refuse. A rejection could also relabel an `uncertain` run as `cancelled`. Both now refuse with `RUN_CLOSED`, checked inside the compare-and-swap update.
3. **Repeated takeovers.** `resume` of a cancelled run that ended `uncertain` took it over again and appended another seal every time. It now returns the run unchanged.
4. **`resume` and `cancel` disagreed.** If the owner had crashed with an idempotent effect in flight, `resume` reported `cancelled` while `cancel` reported `uncertain`. A run taken over with a standing request now skips recovery and settles nodes exactly as `cancel` does. One existing assertion in `tests/cancel.test.mjs` was updated for this.
5. **Close during start-up.** A run cancelled while `foundry run`/`resume` was starting made them fail with `RUN_CLOSED` (exit 1). They now return the cancelled run (exit 3).
6. **Zombie owner counted as alive.** An owner that had exited but whose parent had not collected its exit status still counted as alive. `cancel`, `--force`, `stop-all` and `resume` were all blocked until that parent collected it. `alive()` now treats it as dead.
7. **`stop-all --grace 0` killed every live owner at once.** `cancel --grace 0` only asks. `stop-all --grace 0` now only asks too.
8. **Process identity.**
   - `killOwnerTree` no longer signals an owner with no recorded start time, since its pid may have been reused.
   - `reapChildren` no longer kills a live process group leader whose start time was never recorded.
9. **Effect type.** When settling nodes a dead owner left running, the code ignored the effect type recorded at dispatch. If the registry had changed since, a possibly-completed effect could be reported as a plain failure. Both sources now count.
10. **Busy loop (P3).** `cancelRun` could spin without yielding while a close kept being refused. It now waits one poll interval.
11. **Docs.** The comments claimed nothing is killed over HTTP. In fact, process groups left by dead owners are reaped. Comments and docs are corrected.

## Residual risks (not fixed)
- **Uncharged model call.** A model call recorded in the journal just before the owner died is not charged when cancel closes the run. My probe showed run cost 0 against 0.25 in the journal. verify-run still says ok but warns `JOURNAL_ROW_UNREFERENCED`. This is noted in `docs/ARCHITECTURE.md`. Fixing it means adding a charge step to `closeCancelled`, which needs its own design pass.
- **Unrecorded spend.** Killing a dead owner's model CLI leaves no journal row.
- **Unresponsive providers.** A model provider that ignores its abort signal still holds the run until its own timeout.
- **Escaping a group kill.** A process that leaves a model CLI's process group (via `setsid`) survives the group kill. Sandboxes are not affected: their PID namespace is torn down with them.
- **Long-gap reaping.** Reaping a group whose leader is gone could, in theory, hit a reused group id after a long gap.
- **Frozen owner.** If the canceller dies in the moment between freezing the owner and killing it, the owner stays frozen, possibly holding the database write lock. The window is milliseconds.
- **Other containers.** An owner in another PID namespace looks dead, so a canceller there would close a live run.
- **`--force` takes down the whole owner process.** Other runs it was executing become resumable dead-owner runs.
- **Server-owned stuck runs.** A stuck run owned by the `serve` process itself cannot be cancelled from inside that server.
- **Engine hash changed.** `runtime.mjs` and `children.mjs` changed again, so earlier runs hit `ENGINE_DRIFT` on resume; `cancel` still closes them.
