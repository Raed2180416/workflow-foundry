# ARC interface map (2026-10-06, read-only inspection)

## Summary
ARC (/home/raed/.agentic-os, branch codex/semantic-v2-product-splice-20260811, HEAD 0ada3bf2, last scripts/ change 2026-09-04) is a local-first, evidence-governed agent runtime built around a ~9B local model. Its real backbone is TaskRuntime (scripts/task-runtime.mjs, 12k lines) sitting on EventKernel (scripts/event-kernel.mjs, 10k lines). EventKernel is an append-only, hash-chained events.jsonl per project, protected by an O_EXCL lock and torn-tail repair, with content-addressed artifact stores. Event and contract schemas are closed and versioned (TaskEvent 9.0.0, unknown fields rejected; scripts/contracts.mjs). On top of that sit typed task states and transitions, leases, CapabilityGrant/ApprovalDecision contracts, a deny-by-default CapabilityPolicy, write-ahead runEffect/runTool with idempotency and in-doubt reconciliation, PlanGraph v1 (15 node kinds, per-node authority and budgets), bounded dynamic branch schedules with exact joins, durable operator questions, and read-only replay/projection for the Rust TUI over ws://127.0.0.1:8787/v0.

Maturity, observed: the product path reaches a frozen TaskSpec, then GraphControl, then a candidate that is materialized and evaluated. It stops on purpose before effect and completion. product-task-terminal-bridge-v1.mjs:232 still returns 'candidate-specific effect and promotion transaction is not installed'. ARC's own handoff calls this the P0 launch blocker. ARC's docs say outright that it is substrate, not a product-proven system. Many modules are dark: no production importer was found for provider-routing-policy, multi-agent-orchestration, observability-governance or the LangGraph adapter, and calibrated-routing is imported only by provider-routing-policy. The ARC daemon (8787) and the 9B server (8095) were not listening at inspection time. The working tree is dirty (129 deleted skill files, 5 modified, 30 untracked). Docs that COMPLETE_HANDOFF.md cites (docs/TASK_RUNTIME.md etc.) were deleted on 2026-07-29.

Routing: what is actually live is selectSpecialist in specialist-registry.mjs (guard-first; only 3 of 19 specialists are 'verified', and everything else falls back to the 9B) plus the skill-router. There is also a legacy keyword-tier model-router and an unwired calibrated/provider-routing policy. The 'competence/independence graph' that would drive learned routing is design-only.

Integration stance (inference, but grounded in ARC's own docs): Foundry should be the procedure/workflow IR and builder. It compiles to ARC PlanGraph and TaskDelta proposals and asks for effects through TaskRuntime.runEffect with ARC-issued CapabilityGrants. It reads ARC replay and projections for inspection. It must not build a second durable lifecycle owner, effect ledger, capability issuer, completion authority, or a parallel model/specialist router. Foundry's meta-harness router should sit at the procedure layer, choosing workflow and harness templates, and should hand model/specialist choice to ARC's selector, or extend it through ARC's calibrated-routing contracts. ARC's handoff explicitly forbids giving LangGraph/Temporal/n8n durable or completion authority, and the LangGraph adapter declares checkpointAuthority 'acceleration-only'. The cleanest portable seams are the dependency-free plan-graph-v1.mjs and task-delta-v2.mjs (node:crypto only), contracts.mjs, and capability-policy.mjs. TaskRuntime and EventKernel pull in more than 75 imports each, and the dossier recorded a module-load failure ('readdown') in wider suites.
