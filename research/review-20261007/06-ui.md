## 0. Short answers

1. **Yes, it makes sense, and it is built as a prototype.** `tools/run-view/index.html` shows a run as a few simplified nodes. Each node has a
   coloured dot that breathes while that part is active, a one-line live note, and a click opens its transcript (prompt, typed reply, checks,
   escalations, costs, receipts). It replays a recorded run with play, pause, speed, step and "next notable moment", and it can follow a run live
   through a read-only server. [M] 73 browser checks and 19 unit tests pass (`headless-check.mjs`, `core.test.mjs`); screenshots are
   `research/review-20261007/ui-*.png`.
2. **Two things to set expectations on.**
   - *Most nodes are not model nodes.* The seven workflows the C0 and gate builders actually produced have 4 to 9 root nodes, and 25 of their 44
     root nodes are `code` (57 %), 11 `agent`, 6 `verify`, 2 `map` [M] (appendix B.7). The interesting colour changes therefore happen on the few
     judgement nodes, and the view folds the rest.
   - *The "chat" is a read-only transcript of journaled calls, not a conversation.* A person cannot type into a node. Answers to `human` nodes
     and approvals stay in the existing `web/` flows, which keep their token and their controls. A viewer that can act would give untrusted
     model text a path to authority (section 6).
3. **It is a read-only run inspector, not a visual builder, and that is inside ROADMAP section 3.** Section 1.2 argues it. The page folds records that
   already exist (the hash-chained events, the model-call journal, the pinned workflow version). It adds no store, no write route and no
   dependency.
4. **The example in the owner's message cannot be built yet.** A "visual understanding" node needs an image input. Agent inputs render only
   `json` or `text` (`schemas/workflow.schema.json:63`, `src/context.mjs:49-53`). The prototype's game-QA fixture uses text stand-ins for
   screenshots and says so in its title. What the viewer needs once images exist is in section 8.
5. **Headline numbers.** [M] unless marked.
   - *Diagnosis reach.* Of seven questions about a finished run ("did an independent oracle agree", "which item failed and why", "which model
     escalated to which", "why", "what was it asked", "what did it answer and cost", "which inputs and were they untrusted"), the run view
     answers 6 fully and 1 partly within 2 clicks, with no raw JSON. The existing `web/` UI answers 3 fully and 2 partly, needs 6 clicks and raw
     JSON for the in-item facts, and cannot show a prompt, a reply or the oracle at all (section 7.1; baseline counted by hand on the same run,
     n = 1, no user study).
   - *Folding.* The 10 workflows tried go from 2-15 raw nodes to 2-8 cards at "Simple" (median 6 to 5, section 2.4).
   - *Scale.* A 1000-item map written by the real runtime folds in 45 ms for 7,418 events; the overview stays at about 475 DOM nodes; 16x replay
     holds 16.7 ms per frame. A static 1000-node graph opens as 9 stage cards in 0.4 s. A viewer attached to a running 250-item run costs the
     writer nothing measurable (10.4 and 10.7 s with, 10.6 and 11.2 s without).
   - *Live feed.* Commit-to-browser lag: p50 12 ms, p95 23 ms while following a 250-item run (100 ms poll; separate writer process).
6. **The viewer is not the bottleneck at 1000 items; the writer is.** [M] The real runtime took 1.98, 10.8, 42.5 and 168 s for 100, 250, 500
   and 1000 scripted items (326, 148, 74, 38 events per second). Each event rewrites the whole run blob, which is 829 KB at 1000 items and costs
   about 40 ms of size-proportional work per event at that size (appendix B.5). That is an algorithm, not a language, so it matters for lane 4's
   Rust question.
7. **What the records cannot say, and the view says so on screen.** No event marks a model call leaving the concurrency queue; the event that
   escalates after a failed check does not say which check failed; a map's item total is unknown until it ends; journal replies are not bound to
   the chain. Section 2.8 lists seven gaps with one-field fixes. They need engine changes, so they wait for the P1 freeze.
8. **Decisions needed** are in section 9: where the page lives after the C0 freeze, whether constructors emit a view sidecar, and which runtime
   fields to add first.

## 1. The ask, the scope and what exists

### 1.1 What was asked
- A node-like picture of a workflow, simplified (a "visual understanding" node in a game-QA workflow, "something else" next to it).
- A small breathing dot per node, with colour for state.
- A slight, live note of what is happening inside the node now.
- Click a node to expand its chat.
- Lane 1 recorded this as requirement #67 and judged it **partial**: `web/app.js` lays out the DAG and colours status but has no model-call
  transcripts, receipts, escalations or live stream (`01-requirements.md`, row 67 and the box after section H).

### 1.2 Scope, argued against ROADMAP section 3
ROADMAP section 3 lists "a visual builder or connector catalog" and "tracing UIs or a general eval platform: emit OTel, build only qualification
rules" among the things we do not build [D: `docs/ROADMAP.md:617-631`]. The new direction does not change that, because this is neither:

| Non-goal | Why the run view is not it |
|---|---|
| Visual builder | It has no edit, drag, connect or save. Workflows are still made in IR and code. Its only input is a finished or running run. |
| Tracing UI / eval platform | It is a fold over three records Foundry already keeps (events, journal, workflow version). It keeps no data of its own, takes no spans from other systems and scores nothing. OTel export (ROADMAP 2.10) stays a separate, later job. |
| General agent loop | It starts nothing. The server is read-only and opens SQLite with `readOnly: true`. |

ROADMAP 2.10 already requires "web UI decision cards for each selection, each escalation and each promotion" with the exit criterion that the
owner can answer "why did this happen?" in under 2 minutes [D: `docs/ROADMAP.md:560-572`]. This view is the escalation half of that, for runs. What
it does **not** do: selection cards and promotion cards (no such events exist yet), alternatives with scores, and the 2-minute test with a person.

### 1.3 What exists today (the baseline)
- `web/app.js` (1,072 lines) lays out the static workflow DAG and colours node status from the run record [D: `web/app.js`]. It polls every 3 s
  [D: `web/app.js:1062-1064`] and re-fetches `GET /api/runs/:id`, which returns the whole run **and every event, chain-verified on each call**
  [D: `src/foundry.mjs:98`, `src/store.mjs:151-161`, `src/http.mjs`].
- A node's inspector shows its definition (checks as raw JSON), its recorded output as raw JSON, and a "Node events (n)" list of raw JSON. Nested map
  and loop frames need "Open nested flow", then an iteration choice, then the node [M: driven in this lane, `ui-0-baseline-existing-web.png`].
- It has no route for the model-call journal, so a prompt or a reply cannot be shown (`src/http.mjs` has no such route; `src/journal.mjs` is not
  imported there).
- [M] On the real run used here, the Run-evidence tab's text is 212,391 characters (an events list), and reaching the failed item's events took 6
  clicks (run, node, "Open nested flow", iteration, node, "Node events") and then reading 7 events as raw JSON.
- The UI tests are `tests/ui-contract.test.mjs` (static rules: no `innerHTML`, no inline style, no CDN; lines 110-121), `tests/ui-browser.test.mjs`
  and `tests/ui-trials-browser.test.mjs` (opt-in lanes). The run view obeys the same static rules; `headless-check.mjs` repeats them.

### 1.4 Why the prototype lives in `tools/run-view/`
`web/` is copied into the frozen C0 construction kit (kit hash `7e8f0f83153c5efb`; commit `450ce53` restored it after an earlier attempt put the

## 2. The data model

### 2.1 Three records and one join

| Record | Where | What it gives the view | Bound to the chain? |
|---|---|---|---|
| Events | `events` table, one row per event, `seq`, `previousHash`, SHA-256 [D: `src/store.mjs:143-150`] | Every state change, with times, models, costs, receipts, outputs | Yes |
| Model-call journal | `model_calls` table [D: `src/journal.mjs:28-95`] | The prompt, system prompt, schema, raw reply, typed value, usage and latency of every call, joined by `journalId` on `model.called` | The **prompt** is: `context.compiled.receipt.promptHash` is in the chain and the journal row names its receipt. The **reply** is not (the event carries no response hash, lane 7 section 4.1). |
| Workflow version | `workflows` table, addressed by hash [D: `src/store.mjs:31`] | The node list, needs, descriptions, checks, model classes | Yes (the run names the hash; the exporter re-hashes it) |
| Decisions | `decisions` table [D: `src/store.mjs:43`] | The rationale text of an escalation | No (INSERT OR IGNORE, lane 7) |
| External evidence | an experiment's results JSONL, joined by `meta.runId` | "Independent oracle passed or failed", score, split | Outside the run |

The exporter (`tools/run-view/export-run.mjs`) re-verifies the chain exactly as `Store.events()` does and refuses to export a broken run. It checks
that each journal prompt hashes to the receipt the chain committed to [M] (26 of 26 prompts in the real run; a prompt edited afterwards is flagged,
tested in `core.test.mjs`). It does not read `.foundry/` through `Store`, because opening a store creates tables and changes permissions.

**Node keys.** A node instance is a path: `root/dates:2/judge` is node `judge` in frame 2 of map `dates`. A segment `id:N` names a frame of a map or a
loop [D: `src/runtime.mjs:332-339, 436-470`]. The container's own key has no index (`root/dates`). Nesting is capped at depth 6
[D: `src/validate.mjs:165`], at most 500 nodes per flow [D: `schemas/workflow.schema.json:89`] and 2,000 in total [D: `src/validate.mjs:146`].

**Event vocabulary.** The runtime writes 37 event types (appendix A). Across all 76 workspaces on this machine (154 runs, 10,677 events) only 18
of the 37 occur [M: scan in appendix B.6]: `retry`, `waiting`, `human`, `approval`, `uncertain`, `verify.failed`, `oracle`, `recovered` and `handled`
never appear in a recorded run. The states they drive were therefore checked on **fixtures written by the real runtime with a scripted
provider**, not on recorded runs. That is real runtime output, not real model behaviour.

### 2.2 The reducer
One pure reducer (`RunModel.apply(event)`) turns events into node instances, frame items and run totals. Replay applies recorded events in order;
the live feed applies them as they arrive; both call the same function. This is the main design choice: a recorded view and a live view cannot
disagree, and a bug in one shows in the other.

- An **instance** holds status, phase, state, attempts, model, escalations, retries, check failures, cost, the journal ids of its calls, its
  turns (the events), the last note, and aggregate counters that roll up to every ancestor container.
- A **container** (`map` or `loop`) holds its **items** (frames). An item holds the keys of its leaf nodes and a result.
- **Cost** is charged once per journal row, as the runtime does (`chargeModel`, `src/runtime.mjs:647`), because a crashed run can emit the event again.

[M] `core.test.mjs` runs four workflows through the real runtime (finished, paused, env-fault, nested) and compares the
reducer's status for **every node instance** with the runtime's own checkpoint (`run.nodes`, `run.frames`), plus cost to 1e-9, the call count to the
journal row count, and replay determinism. All agree. Fuzzing (dropped, duplicated, shuffled, unknown-type and field-stripped events) never throws.

### 2.3 States, colours and their sources

Sixteen states. Colour says what kind of attention the part needs; a **glyph** and **words** repeat it, so colour is never the only signal.

| State | Colour | Glyph | Motion | What drives it (events) | Words on screen |
|---|---|---|---|---|---|
| idle | grey | hollow | none | no event for this instance yet | Not started |
| queued | blue | hollow ring | slow breathe, 4 s | `context.compiled` (recorded exports: until the derived dispatch) | Context ready, waiting for a model slot |
| calling | blue | three dots | breathe, 2.6 s | derived `model.dispatched`; in a live feed, `context.compiled` | Waiting for the model / Asking haiku-5-5 (2.1 s) |
| running | blue | solid dot | breathe, 2.6 s | `node.started`, `tool.intent`; code, task, verify between events | Running code in the sandbox / Running tool qa.step |
| retrying | amber | retry arrow | fast, 1.2 s | `model.retry` (E1), `tool.failed` | Retry 1: MODEL_SCHEMA |
| checkfailed | amber | bang | fast, 1.2 s | `model.resampled` (E2, transient); a **non-gating** verifier that completed with `pass: false` (persistent) | Check failed, resampling / Verifier reported problems |
| escalated | violet | up arrow | breathe | `model.escalated`, until the node ends; stays as a chip after | Check failed, escalated haiku-5-5 to sonnet-5-5 |
| waiting | slate | clock | slow | `node.waiting` (timer), `node.waiting_child` | Waiting until 08:19:22 UTC |
| needsyou | pink | question mark | attention, 1 s | `human.requested`, `approval.requested` | Waiting for your answer: ... / Needs your approval: qa.file_bug |
| done | green | check | none | `node.completed` | Done in 1.4 s for $0.00015 |
| handled | amber | check | none | `node.handled_error`; a map or loop that finished with collected item failures | 4 items: 3 done, 1 failed (collected) |
| failed | red | cross | none | `node.failed` | Failed: MODEL_ESCALATION_EXHAUSTED |
| envfault | red, hatched | plug | none | `node.failed` whose code is an environment fault: `MODEL_RATE_LIMIT`, `MODEL_UNAVAILABLE`, `MODEL_TIMEOUT`, `MODEL_PROTOCOL`, `MODEL_BUDGET`, `SANDBOX_UNAVAILABLE` | Environment fault: MODEL_RATE_LIMIT. Not escalated |
| uncertain | red | tilde | none | `effect.uncertain` | An effect may have happened; needs reconciliation |
| skipped | grey | dash | none | `node.skipped` | Skipped |
| cancelled | grey | slash | none | run ended while the node was still running, or `CANCELLED` | Stopped with the run |

Palette (dark / light): blue `#5eb6f5` / `#0a68b0`; amber `#f4b740` / `#a95f00`; violet `#ab9bff` / `#5b3fd0`; slate `#8fa8c8` / `#4a6285`; pink `#f08cc0` / `#b0206b`;
green `#3fcf9b` / `#08764f`; red `#ff7b6b` / `#bf3a2b`; grey `#77879d` / `#667689`.

Rules that keep the colours honest:
- **Never green when it is not.** A map that collected an item failure is `handled` (amber check), not `done`. A verifier that said `pass: false`
  and did not gate the run is `checkfailed`. "Succeeded" on the run pill reads "Succeeded locally" with the runtime's verdict beside it ("does
  not establish completion"), and a second pill says "No independent verification attached" or "Independent oracle FAILED" [D: README.md, "What this is": a valid schema, a successful model response and a verified task outcome are three different results]. On the real run the oracle failed (score 0.9465, development
  split) while the run said succeeded; the view shows both.
- **An environment fault is not the model's fault.** The runtime throws instead of escalating or retrying on a larger model
  [D: `src/runtime.mjs:626`], `onError: continue` and `failure: collect` cannot hide it [D: `src/runtime.mjs:46-50`], and the view gives it its
  own hatched red so nobody reads it as a weak model.
- **Attention beats calm when parts are combined.** A group shows the highest-priority state among its members: needs-you, uncertain, failed,
  env-fault, escalated, check-failed, retrying, calling, queued, running, waiting, handled, done, skipped, cancelled, idle. A half-finished group
  (some done, some not started) is "running", never done.
- **Motion encodes activity, and its speed encodes urgency** (4 s idle-but-pending, 2.6 s working, 1.2 s trouble, 1 s needs you). With
  `prefers-reduced-motion` or the "Motion off" button the animation stops and active states keep a static ring, so they stay distinguishable [M:
  `headless-check.mjs`, reduced-motion context: animation name is `none`].
- When a run ends while a node is still "running", the node becomes `cancelled`; it must not keep breathing.

### 2.4 Semantic nodes: how frames and steps collapse

The graph shows **semantic nodes**, not workflow nodes. Three detail levels (a slider): **Raw** (one card per workflow node), **Normal** (fold
chains and preparation steps), **Simple** (also fold wide fans, and stage-fold very large graphs). The page opens at Simple when Normal would still
need more than 10 cards, and stops auto-choosing once the reader moves the slider.

Frames collapse **always**, at every level: a `map` or `loop` is one card ("×N" chip, a progress bar of done, failed, active and queued
items); its body never becomes cards on the main graph. The card opens a drawer that goes *items, then one item's parts, then a node's
transcript*, with breadcrumbs (`Cases › item 1 › Settle › iteration 2 › Step`). A frame with one part skips the list. This is how nested
containers (a loop inside a map) stay readable [M: `zoo-nested` fixture: 3 cards for 5 workflow nodes and 3 nested loops; reducer agrees with the checkpoint].

Folding rules (levels 1 and 0 unless noted; `det` = `code` or `assert`):

| Rule | Condition | Result | Level |
|---|---|---|---|
| Authored | the sidecar names a group (`viewHints.groups`) | those nodes are one card with the authored label; later rules leave it alone | all |
| R1 chain | a `det` node has exactly one remaining need, that need is `det` and has exactly one consumer | the two are one step ("Spec → Prep") | 1, 0 |
| R2 prep | a `det` group feeds exactly one model or container group | it becomes that node's preparation ("Includes: ...") | 1, 0 |
| R4 fan | three or more single model or container nodes with identical inputs and identical consumers | "6 parallel judgements" (or "reads" for maps) | 0 |
| R5 stage | still more than 24 cards | fold by dependency depth into at most 12 "Stage n" cards, with progress over their steps | 0 |

(R3 does not exist; the numbering follows the code comments.) Edges drawn are the **transitive reduction** of `needs`, so a consumer is not linked to
a producer it only reaches through another node. Authored groups are never merged by R5.

**Labels**, first hit wins: (1) the authored sidecar label (`viewHints.labels[id]`); (2) the humanised node id ("Atlas switch") when the id is readable;
(3) the first 28 characters of the node's `description` when the id is generic (`n1`, `step3`, fewer than 3 characters). The IR's own `role` field
on agent nodes adds a plain-words verb in the drawer ("sorts into categories", "reads and extracts", "combines findings"). Labels are a sidecar
because the node schema has no label or display field and `additionalProperties` is false [D: `schemas/workflow.schema.json:94-96`]; adding one
would change the workflow hash. The sidecar is `{labels: {nodeId: text ≤ 60}, groups: [{label, members}]}`, shape-checked on export and on load,
treated as text, with no authority.

**The `call` frame (not in the IR today).** Lane 2 proposes a `call` node that runs a child workflow with its own run record and keeps node keys

cost is the parent's plus the child's roll-up, and whose drawer opens the child's view with the path as breadcrumbs. The reducer already keys
by path, so a child run is a second `RunModel`.

### 2.5 The live line: where the one-line note comes from

Every line is a **template over typed event fields**: codes, ids, numbers, models, durations. **Model-written text never appears in a card line.**
(The only free text is a `human` node's question, which the workflow author wrote, clipped to 70 characters.) A fresh note (the last retry,
resample or escalation, for 7 s of recorded or wall-clock time) is put before the current activity, because a retry returns the node to "asking
the model" within a millisecond and the reason would vanish.

| State or situation | Template | Fields |
|---|---|---|
| queued / calling | `Asking {model} ({age})`; live feed: `Context ready, waiting on {model} ({age})` | `context.compiled.modelId`, derived dispatch time |
| running code or tool | `Running code in the sandbox ({age})`, `Running tool {tool} ({age})` | `node.started.kind`, `tool.intent.tool` |
| retry | `Retry {n}: {errorCode}` | `model.retry.retry`, `.errorCode` |
| check failed, resampling | `Check failed, resampling (sample {n})` | `model.resampled.sampleIndex` |
| escalated | `Check failed, escalated {from} to {to}` or `{errorCode}, escalated ...` | `model.escalated.rule`, `.errorCode`, `.fromModel`, `.toModel` |
| waiting | `Waiting until {hh:mm:ss} UTC`, `Waiting for child steps` | `node.waiting.wakeAt` |
| needs you | `Waiting for your answer: {question}`, `Needs your approval: {tool}` | `human.requested.question`, `approval.requested.tool` |
| done | `Done in {duration} for {cost}, escalated {n}x` | start and end times, `costUsd` sums |
| failed / env fault | `Failed: {code}`, `Environment fault: {code}. Not escalated` | `node.failed.error.code` |
| map | `{k} of {total}+ finished, {a} active, {f} failed. Item {i}: {note}` | item counts from `frame.created`, `map.item.*` |
| loop | `Iteration {n} of at most {max}`; done: `{n} iterations` | `frame.created`, the definition's `maxIterations` |
| stage (R5) | `{done} of {total} steps done, {a} active, {f} failed` | member states |

The counters tick every 250 ms while playing, so "(2.1 s)" moves without any event. In replay the time is the recorded time, interpolated
between events; in a live feed it is the wall clock since the last event.

### 2.6 The transcript panel

Click a card and a drawer opens. For a single node it reads like a chat, in event order:

1. **Header and facts:** state, plain-words role, what the node does (the `description`), duration, model and class and escalation history,
   allowed models (`model.class`, `maxClass`), call count and cost, the error.
2. **Context compiled** (`context.compiled`): tokens, budget, receipt hash, and a table of every input with its **trust label** (`trusted` or
   `untrusted:source`), tokens, source reference and truncation. Untrusted labels are amber chips with a note that they cannot grant authority.
3. **Left the queue; call in flight**: a derived event, marked as reconstructed from the journal latency.
4. **Prompt sent to {model}:** attempt, sample, mode, reasoning setting, prompt hash, a green "prompt matches the chain receipt" chip (or a red
   one if it does not, or an amber "not checkable"), the system prompt (collapsed), the user prompt, the required output schema (collapsed).
5. **Reply from {model}:** latency, tokens in and out, cache read and write, cost, "live call" or "replayed from journal", an amber "reply:
   journal row, not bound to the chain" chip, the **typed value** (parsed against the schema), and the raw reply (collapsed).
6. **Retry** and **resample** turns (rule E1 or E2 and the code or reason), and the **escalation** turn: from and to, class, rule, error code,
   money spent so far, and the decision record's rationale.
7. **Final output** (hash, bytes, label, the JSON), or **Error** (code, message, and a sentence on what that class of error means), or **Verifier
   said the subject fails** (the verdict and reasons).
8. **Receipts:** the journal rows of the node (id, model, provider and engine, receipt hash, cost) and the event numbers in the chain.
9. **Definition** (collapsed): code source (clipped in the export), instructions, output schema, the **checks** as JSON, escalation rules.

For a container it shows facts, filters (All, Active, Failed, Escalated, Done with counts), an SVG waffle of up to the whole item set (one square per
item, 40 per row; clicking opens the item) and a list capped at 60 rows with a "narrower filter" note. For a fan or stage it shows the parts. Opening
a group never builds DOM per item: [M] 1000 items open in 42 ms and add about 1,000 DOM nodes, of which 503 are the waffle.

### 2.7 The summary strip
Run status (from the runtime), the runtime's verdict and its authority, the external oracle result when one is attached (with its split:
development or sealed), recorded time, spend against the cap, model calls, escalations, check failures, and a chain-verification pill ("Chain
verified at export" or "Chain checked as it streams"). In a live view it adds a connection pill, a count of events waiting while paused, and
"No event for 42 s" after 10 s of silence, because a long model call and a dead runner look the same on screen [I; the first is documented,

## 3. Streaming transport

### 3.1 What polling costs today
[M] on the 1000-item run (6,316 events): `GET /api/runs/:id` returns 4.1 MB and verifies the whole chain on each call (86 ms); at 250 items it is
1.03 MB and 25 ms, at 100 items 0.42 MB and 8 ms. The existing UI refetches whenever `updatedAt` changed, every 3 s. For the 168 s run that is about
56 requests, an average of about 2 MB each, so roughly 115 MB moved to show a 2.3 MB history [I: computed from the measured sizes; not run].

### 3.2 The design (built: `tools/run-view/serve.mjs`)
**SSE from the existing event table.** One-way, built into browsers (`EventSource`), resumes by itself with `Last-Event-ID`, needs no dependency,
passes `connect-src 'self'`.

| Route | Returns |
|---|---|
| `GET /api/runs` | the workspace's 50 latest runs (id, title, status, counts) |
| `GET /api/runs/:id/view` | run header, the pinned workflow version, the decision records. No events. |
| `GET /api/runs/:id/stream` | SSE. `event: batch` with up to 400 slim events, `id:` = last `seq`; `event: end` after a terminal run event; `event: integrity` and stop if a row fails the chain check; a `: ping` comment every 15 s |
| `GET /api/runs/:id/call/:journalId` | one journal row (prompt, reply, typed value), when a transcript is opened |
| `GET /api/runs/:id/output/:seq` | one event's full output (the stream sends outputs of at most 2 KB inline) |

- **Wake-up.** `PRAGMA data_version` changes when another connection commits. An idle stream costs one pragma per tick (100 ms default). [I] The
  alternative, an in-process hook in `Store.updateRun`, is faster but misses runs written by another process (the CLI, `foundry tick`, another
  agent); keep the pragma as the rule and add the hook later as an optimisation.
- **Verification on arrival.** Every row is checked: `seq` is the previous plus one, `previousHash` equals the previous row's hash, and the digest of
  the body equals its stored hash. A failure sends the rows that did verify, then `integrity`, then stops. [M] tested by editing event 12 of a
  finished run: the page receives events 1-11 and shows "Stream stopped: the event chain does not verify from here".
- **Slim events and lazy bodies.** The page gets an event without its chain hashes (a 16-hex marker stays) and without outputs over 2 KB; prompts
  and replies are fetched when a drawer opens. [M] 366 bytes per event on average.
- **Slow clients.** The server reads the next rows only when the socket has drained (`writableNeedDrain`), so a stalled browser is not buffered
  without bound. (Written; not load-tested.)
- **Resume.** The browser's reconnect sends `Last-Event-ID`; the server re-checks the chain from that row. A finished run streams from the start.
- **Security.** Loopback only; Host, Origin and `Sec-Fetch-Site` checks as in `src/http.mjs:35-37`; GET only; a per-start random token required on
  `/api`, carried in the URL **fragment** (never sent in a request line), removed from the address bar after load; read-only SQLite handles; fixed
  routes with run ids as bound SQL parameters (no file paths from the request). The token is stricter than `src/http.mjs`, which lets unauthenticated GETs
  read run events: the feed carries prompts and corpus text, which `inspectRun` does not.

### 3.3 Measurements [M]
| What | Result |
|---|---|
| Commit to browser, following a 250-item run, writer in its own process | p50 12 ms, p95 23 ms, max 426 ms (116 batches) |
| Same, following the 69-event game-QA fixture (headless check) | p50 38 ms, p95 355 ms (18 batches; load average 3-6) |
| Stream a **finished** 1000-item run (6,316 events, chain-checked) | 2.3 MB, first byte 31-91 ms, all events 231-355 ms |
| `view` for that run | 56 KB in 27 ms; one `call` row 1.7 KB in 4 ms |
| Writer slowdown with a viewer attached (250 items, two runs each, 4 runs) | 10.4 and 10.7 s with; 10.6 and 11.2 s without. Noise on this machine is about 5 %. |
| Bytes of one live view of 250 items | 583 KB in 105 batches (1,591 events) |

### 3.4 Alternatives
- **WebSocket:** two-way; the view only reads, and a socket we would have to guard for writes is a risk we do not need.
- **Poll the existing endpoint faster:** rejected by 3.1.
- **OTel to a tracing UI:** ROADMAP 2.10 keeps OTel as a separate export, and a tracing UI is a non-goal.
- **Tail the SQLite file in the page:** impossible under CSP and the browser sandbox; also would skip the chain check.

### 3.5 Putting it in `src/http.mjs` later
Five GET routes and one `res.write` loop, reusing the existing host, origin and CSP checks; no new dependency. The server holds one read-only
handle per open stream. Not done now: `src/` is read-only for this lane.

## 4. Performance for 1000-node runs

### 4.1 Which "1000"
The IR bounds what a run can hold: a `map` has at most 1000 items (`maxItems`), a `loop` at most 1000 iterations, a flow at most 500 nodes, a workflow
at most 2,000 nodes [D: `schemas/workflow.schema.json`, `src/validate.mjs:146`], and the runtime stops a run at a 10 MiB state blob
[D: `src/runtime.mjs:235`], which at 829 bytes per single-node item frame is about 12,000 frames or about 72,000 events. Three shapes matter:
**1000 item frames** (a map), **1000 static nodes** (a large workflow), and **72,000 events**.

### 4.2 Design for scale
- **A dirty set and one `requestAnimationFrame`.** An event marks the top-level card it touches; rendering redraws only those cards and only when
  their text, state or chips changed (a cache per card). Edges are redrawn when the layout changes, restyled when states change.
- **No DOM per item.** Items exist as reducer objects and as one SVG square each in the open drawer; the list is capped at 60 rows.
- **Stage fold** (R5) bounds the card count at 12 stages however large the graph.
- **Replay** applies events up to a virtual time per frame (clock capped at 250 ms per frame); a backward seek resets the model and re-applies (O(n)).
- **Idle gaps** are shortened (2 s maximum) and notable moments held for 1.2 s, so a 50 s run is watchable and a one-event escalation is visible.
  The checkbox turns both off for true recorded time.

### 4.3 Measured [M] (Chromium, 1440x900)
| Case | Result |
|---|---|
| Fold 7,418 events of the 1000-item run | 45 ms |
| Fold up to 72,004 events (12,000 items), node script | 228 ms; 3.2 to 6.5 microseconds per event, linear |
| Jump to the end / back to the middle of that run | 25 ms / 14 ms |
| Overview DOM, 1000-item run | 475 nodes (388 for the 15-node real run) |
| Open the group drawer | 42 ms, 1,499 DOM nodes (503 waffle squares, 60 rows) |
| 16x replay for 6 s | 359 frames; median, p95 and max 16.7, 16.7, 16.8 ms; 2,639 events applied; render mean 0.83 ms, max 2.9 ms |
| JS heap after loading 7,418 events and all state | 19 MB |
| Following a **live** 250-item run | frame p50 16.7 ms, p95 16.7 ms; render mean 0.58 ms; no console issues |
| Following a **live** 1000-item run (164 s, 6,316 events, 1,630 batches) | frame p50 and p95 16.7 ms, max 66.7 ms; commit-to-browser lag p50 34 ms, p95 69 ms, max 498 ms; render mean 0.53 ms, max 3.7 ms; JS heap 7 MB; no console issues |
| Static 1000-node graph (25 layers of 40) | 9 stage cards, ready in 399 ms, 414 DOM nodes; the semantic fold takes 84-134 ms at the three levels |
| The same graph at Raw | 1,000 cards, 16,502 DOM nodes, ready in 931 ms (a scratch measurement before the stage fold existed; Raw is unchanged by it). The reader asked for it; it is unreadable. |
| Page source | 102 KB JS, 15 KB CSS, 5 KB HTML; one-file bundle of the real run 551 KB |

### 4.4 The writer is the slow part (a finding for lane 4)
[M] Real runtime, scripted provider (4-10 ms calls), 16 concurrent items:

| Items | Events | Wall time | Events per second | Run blob |
|---|---|---|---|---|
| 100 | 643 | 1.98 s | 326 | 85 KB |
| 250 | 1,591 | 10.8 s | 148 | 209 KB |
| 500 | 3,166 | 42.5 s | 74 | 416 KB |
| 1000 | 6,316 | 168 s | 38 | 829 KB |

Doubling the items quadruples the time: the cost per event grows with the run. [M] At the final 829 KB blob, per event: parse 3.6 ms, `canonical()`
19.9 ms, `checkData` 5.6 ms, `clone` 11.6 ms, about 40 ms in all [M: appendix B.5]. [D: `src/store.mjs:127-141`] `updateRun` loads the whole blob, runs `checkData(run, 12 MB)`, mutates it,
and writes it back with `canonical(run)` on every event, under `PRAGMA synchronous=FULL`. [I] A Rust port would make each pass faster but would not
change the shape; the fix is to stop rewriting the whole run per event (frames as rows, or an event-sourced fold), which also removes the
12-MB-blob ceiling. The same loop holds the run at 38 events per second at 1000 items regardless of model speed, so it would be the first thing
a 1000-item run on real Haiku calls (about 1.5 s each, 16 at a time, about 10 calls per second) would hit; with those numbers the model is
slower than the writer at 100 items and the writer slower at 1000 [I].

### 4.5 Limits
Raw detail on a very large graph is unreadable by design. A single container with more than a few thousand frames (beyond what the 10 MiB state
budget allows) is untested. Memory for 72,000 events was not measured in the browser. The time to first paint of a 10-MB export was not measured.

## 5. Accessibility

What is built, and how it is checked [M] unless marked:
- **Colour is never alone.** Every state has a glyph and words; the legend lists all sixteen. [M] 46 contrast pairs (state colours on cards, glyph ink on
  fills, three text greys on page and card, the accent) pass WCAG 3:1 for graphics and 4.5:1 for text in both themes; the minimum is 4.65:1.
- **Dark and light themes**, following `prefers-color-scheme`, with a button. `forced-colors` has a fallback block (not tested in a browser).
- **Reduced motion:** `prefers-reduced-motion` and a "Motion off" button stop every animation; active states keep a static ring.
- **Keyboard:** Tab reaches skip link, controls, cards, drawer, player. Arrow keys move between cards by column and row. Enter opens the
  transcript and **moves focus into it**; Escape closes it from anywhere (including the sliders) and returns focus to the card. `p` play,
  `,` and `.` step, `[` and `]` previous and next notable moment. Live refreshes rebuild the drawer and put focus back on the control at the same
  position [M: Enter and Escape are tested; the refresh restore is built and was exercised by the live check, not asserted separately].
- **Names:** every control has an accessible name; every card's name carries label, state, live line, count and role. One `h1`, a labelled graph
  region, a polite live region. [M] checked.
- **Announcements:** a polite live region says a node changed to needs-you, failed, env-fault, escalated, check-failed or uncertain (and done after
  activity), with a 1.5 s floor and "N more updates" when several arrive at once, so a 1000-item run does not read out a thousand lines.
- **Phone width:** at 390 px the page does not scroll sideways and the drawer takes the full width [M]. The player takes a large share of the screen
  there; usable, not pleasant.
- **Not done:** no test with a real screen reader (unknown whether the announcements are tolerable), no zoom-to-400 % check, no high-contrast
  browser test, and the waffle squares are pointer-only (the list below it is the keyboard route, and the waffle is `role="img"` with a text alternative).

## 6. Privacy and untrusted content

Everything the page shows can come from task data a hostile source wrote: prompts embed corpus text, replies are model output, error messages can
quote either, workflow titles and descriptions come from a model-authored workflow. The rules (`run-view.js` header and `headless-check.mjs`):

| Threat | Mitigation | Test |
|---|---|---|
| Markup or script in any string | Every value becomes a text node (`createTextNode` or `textContent`); attributes come from a fixed set chosen in code. No `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `eval`, `new Function`, `document.write`, `.style`, inline style or handler. | static rules (same as `tests/ui-contract.test.mjs:110-121`) [M]; a hostile run (`<img onerror>`, `<script>`, in prompt, reply, value, title, node description, error message, a view label): no script ran, no `<img>` or `<script>` created, markup visible as text [M] |
| Spoofing with bidi, zero-width or terminal-escape characters | `sanitizeDisplay` replaces control, bidi (U+202A-202E, U+2066-2069), zero-width and lone-surrogate characters with a visible `⟦U+XXXX⟧` and a count | [M] unit and browser |
| Page loads something remote | CSP: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'` from `serve.mjs`; in a one-file bundle, a meta CSP with the script and style **hashes** and `connect-src 'none'` | [M] CSP violations count as failures; the bundle opens from `file://` |
| Content makes the viewer act | The viewer has no action: no approve, answer, resume or cancel. Those stay in `web/` behind its token. A model reply that says "approve this" has nothing to click. | by construction; the server is GET only and returns 405 [M] |
| DNS rebinding or a hostile web page reads the feed | Host and Origin checks, `Sec-Fetch-Site`, loopback bind, token in the URL fragment | 403 without token, 403 for a foreign Host, 405 for POST [M] |
| Huge strings | Prompts clipped at 40,000 characters, other strings at 3,000, with the clip count and a SHA-256 marker recorded in the file and shown in the text | [M] 6 clipped strings (153,108 characters) in the real export |
| Secrets in a shared export | Nine secret patterns (Anthropic, OpenAI-style, GitHub, AWS key id, Slack, PEM private key, Bearer, JWT) and the **values** of environment variables whose names look secret are replaced by `[REDACTED:kind]`; the file is mode 0600 and says it holds prompts. | [M] 0 hits in the real export. **Limit:** regex redaction cannot find a secret of an unknown shape that sits in corpus text. Treat an export like the workspace. |
| An edited journal | The prompt is checked against the chain's receipt; the reply is labelled "not bound". | [M] edit test |
| Trust labels lost on screen | Untrusted inputs are amber chips in the context table; outputs and typed values are introduced as "model output is untrusted data". | by inspection |

What the viewer cannot do: tell whether a *trusted-labelled* value is really trustworthy (labels are the runtime's, lane 7 S2 discusses
laundering), or protect a person who copies a prompt out of the page and pastes it into a tool.
