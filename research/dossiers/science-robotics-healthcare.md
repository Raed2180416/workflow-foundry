# Science, robotics and healthcare workflow systems

Research snapshot: **13 September 2026**. Acquisition and source inspection were performed in `/home/raed/Projects/workflow-foundry`. This dossier covers the science/robotics/healthcare assignment and the subsequently requested Emerald protocol and Skild public surfaces. It separates inspected implementation, interface declarations, documentation claims and proposed Foundry requirements.

The strongest common finding is that workflow quality depends on the boundary between a requested action and independently observed completion. The inspected systems offer useful mechanisms for typed state, scoped tools, analysis composition, device coordination and specialist routing. They also show why a detailed skill file alone cannot supply durable effect accounting, current-world validation, device interlocks or outcome evidence.

## Representative executable traces

### BioNeMo: preflight and candidate evidence

The inspected preflight accepts a target, resolves its identity, acquires relevant structure/context through subprocess calls, computes alignment/context checks and returns a structured result that is also formatted for a human. This is executable admission preparation rather than a generic paragraph of advice. The selected CLI catches per-target exceptions and prints an error. A consumer must therefore inspect the structured result and define failure semantics; a completed CLI invocation is not a universal readiness certificate. Full design inference was not traced. [SCI-B2](../../skills/domain-science/references/source-map.md#sci-b2)

The manifest is the state object for another inspected design workflow. It contains run identity, parameters, filters, stage state, candidate identities, scores, artifacts and control flags. Candidate updates and rankings operate on this object. This is a useful separation between data generation and evidence bookkeeping. Its direct JSON write and path-based artifact references, however, do not provide concurrency-safe mutation or byte-verified lineage by themselves. [SCI-B1](../../skills/domain-science/references/source-map.md#sci-b1)

A concrete static failure case is the filter loop: a configured metric is only tested when present. The final predicate requires at least one evaluated check and all evaluated checks to pass. With mandatory abstract metrics A and B, a good A and missing B can therefore pass the inspected function. Foundry should make required evidence explicit and treat absent B as incomplete. This is a source-derived counterexample, not a locally executed BioNeMo regression or a conclusion about every workflow in the toolkit. [SCI-B1](../../skills/domain-science/references/source-map.md#sci-b1)

The transfer is a two-part contract: the compiler declares the required evidence, and the runtime independently checks its presence, identity, type, units, freshness and predicate. A manifest's provenance establishes how a candidate was produced; it does not establish scientific efficacy. Test the contract with synthetic metrics and artifact mutations, not biological procedures.

### Robin: parallel research, hosted execution and output joins

`robin/analyses.py` creates a data-analysis question and constructs five parallel analysis requests followed by a consensus step. `MultiTrajectoryRunner` iterates steps, uploads declared inputs, expands the task requests, calls the remote Edison execution API with a timeout, summarizes returned statuses, downloads output files, performs post-processing and saves the responses. Configured clients and job names locate the boundary between this public coordinator and hosted agents. [SCI-R1](../../skills/domain-science/references/source-map.md#sci-r1), [SCI-R2](../../skills/domain-science/references/source-map.md#sci-r2), [SCI-R3](../../skills/domain-science/references/source-map.md#sci-r3)

State includes generated step identifiers, optional upload identifiers, step configurations and an in-memory response dictionary. The inspected save path records results after the pipeline; it is not a demonstrated durable resume ledger for every remote dispatch. The remote request helper can omit failed submissions after logging them. A completeness rule must therefore be based on the originally requested branch set, not merely the returned response set. [SCI-R1](../../skills/domain-science/references/source-map.md#sci-r1), [SCI-R3](../../skills/domain-science/references/source-map.md#sci-r3)

The runner catches output-download failures and can still invoke post-processing. The analysis caller subsequently checks its expected CSV and can return an explicit error, so it would be inaccurate to claim the entire system always labels a missing artifact successful. The general issue is that service status, downloaded artifacts and caller-level interpretation are different stages with different failure behavior. Their join needs an explicit contract. [SCI-R1](../../skills/domain-science/references/source-map.md#sci-r1), [SCI-R2](../../skills/domain-science/references/source-map.md#sci-r2)

After reading the data, interpretation is generated through a model and checked for a four-part delimiter structure. This checks output organization; it does not check that every scientific assertion follows from the analysis. Agreement among parallel agents is an additional model judgment with potentially correlated errors. The independently testable part is that every required branch produced its declared artifact under the correct inputs and that claimed observations can be traced to those artifacts. [SCI-R2](../../skills/domain-science/references/source-map.md#sci-r2)

For a model-substitution experiment, replace only a declared architectural or executor role while holding the tool contract, dataset, branch budget, timeouts and oracles constant. Substituting a local inexpensive model for this entire remote service and comparing prose output would confound model, tools and infrastructure.

### Safe Lab: instrument access boundary and evidence limits

The inspected design keeps trusted instrument functions in a host process and exposes a selected tool set to an agent environment. A bearer token is required, registered names are checked and arguments are decoded and validated before invocation. The container manager adds concrete hardening, scoped mounts and resource controls. The firewall's intended policy permits public internet while restricting private-network access except a configured MCP route. These are actual software mechanisms, not merely model instructions. [SCI-L1](../../skills/domain-science/references/source-map.md#sci-l1), [SCI-L2](../../skills/domain-science/references/source-map.md#sci-l2), [SCI-L5](../../skills/domain-science/references/source-map.md#sci-l5)

Incoming NumPy arrays are loaded without allowing pickle. The type checker intentionally validates only the outer container, permits unannotated arguments and bypasses checking when annotations cannot be resolved. Therefore it cannot by itself enforce nested element types, dimensional consistency or the operating envelope of an instrument. A deployment adapter must supply those rules using current instrument state. This finding is about validation completeness, not a claim of unsafe deserialization of incoming pickle. [SCI-L4](../../skills/domain-science/references/source-map.md#sci-l4)

Automatic logging wraps tool functions and captures arguments, results, timestamps and structured data. The wrapper calls the function before creating its record. If the tool throws, that path does not record the failed attempt. If later logging fails, the wrapper warns and can return the successful tool result. Batch metadata can also exist in memory before being written. Shared output locations are writable by the agent. These mechanisms provide useful provenance but do not establish an independent, durable and tamper-resistant effect journal. [SCI-L3](../../skills/domain-science/references/source-map.md#sci-l3), [SCI-L2](../../skills/domain-science/references/source-map.md#sci-l2)

Shutdown attempts a log flush and a configured cleanup hook. Container snapshots save software state and files. Neither mechanism establishes that a physical process has reached a safe state or that restoring a snapshot reverses a laboratory operation. A hardware interlock must remain effective without a functioning model, container, MCP server or network. This is an integration requirement derived from the observed process boundary, not a finding that every Safe Lab deployment lacks hardware protection. [SCI-L1](../../skills/domain-science/references/source-map.md#sci-l1), [SCI-L2](../../skills/domain-science/references/source-map.md#sci-l2)

Resource policy needs a similarly explicit interpretation. The container manager can retry creation without resource limits after a relevant Docker API error. This can be a deliberate portability fallback. It does not satisfy a profile that promises mandatory memory or CPU enforcement. Such a profile should reject admission when the backend cannot enforce it. [SCI-L2](../../skills/domain-science/references/source-map.md#sci-l2)

The portable design is a narrow, authenticated adapter with closed schemas, verified resource policy, versioned tool definitions and protected intent/outcome records. Optional tool reload must produce an explicit schema/capability revision and invalidate affected approvals. The planner can explain and request a change; it cannot make the trusted boundary disappear by restating the request.

### RMF: request, dispatch, robot acceptance and completion

The demo requester builds a task description, binds a UUID request ID and publishes either a direct robot request or a dispatch request. It listens for a matching response for a bounded interval. The ROS dispatcher validates new request shape, starts assignment and returns the initial task state. The public task-state schema distinguishes queued, selected and dispatched states from task execution outcomes. [ROB-D1](../../skills/domain-robotics/references/source-map.md#rob-d1), [ROB-C1](../../skills/domain-robotics/references/source-map.md#rob-c1), [ROB-S1](../../skills/domain-robotics/references/source-map.md#rob-s1)

The demo fleet adapter maintains per-robot execution state and command identifiers. Its navigation callback issues an HTTP command through `RobotClientAPI`. The demo fleet manager turns that request into a ROS path publication and returns success. Later robot-state feedback checks task identity, mode and remaining path; completion propagates through `last_completed_request`, and the adapter finishes the matching execution. This is the representative end-to-end trace: accepted HTTP response and observed execution completion are deliberately different observations. [ROB-D2](../../skills/domain-robotics/references/source-map.md#rob-d2), [ROB-D3](../../skills/domain-robotics/references/source-map.md#rob-d3)

The stop endpoint likewise publishes a request and returns success. That response alone is not a physical-stop observation. The demo's retry loop also continues until success or its cancellation signal. Stronger deployment contracts need an end-to-end recovery deadline, current device epoch, payload-bound command identity and a specified telemetry age bound. These additions address properties not established by the inspected demo, rather than asserting that all RMF integrations use the same simplified policy. [ROB-D2](../../skills/domain-robotics/references/source-map.md#rob-d2), [ROB-D3](../../skills/domain-robotics/references/source-map.md#rob-d3)

The core dispatcher stores a bounded in-memory cache keyed by request ID. It returns a cached response before parsing the new request body. This is a concrete duplicate-response mechanism, but the inspected cache is not a durable, payload-bound exactly-once guarantee. A general external-effect adapter should bind identity to actor, run, workflow revision, device epoch and payload hash and reconcile after a lost acknowledgement. [ROB-C1](../../skills/domain-robotics/references/source-map.md#rob-c1)

Cancellation ownership changes after dispatch: requests that have reached a fleet are no longer wholly owned by the dispatcher. The active-task interface makes the semantics unusually clear. `finished()` can include cancellation. `cancel()` can continue cleanup phases until a completion callback. `interrupt()` acknowledges when other control may be issued and supplies a resumer. `kill()` has a different intended outcome and supersedes cancellation. These software task contracts must not be renamed into a generic hardware emergency stop. [ROB-C2](../../skills/domain-robotics/references/source-map.md#rob-c2), [ROB-T1](../../skills/domain-robotics/references/source-map.md#rob-t1)

The schedule participant API binds itinerary, delays and reached checkpoints to plan identities and versions and exposes rectification hooks for distributed state. This supplies a useful model for versioned progress. Only that interface was inspected: collision avoidance, negotiation correctness and actual-device timing remain outside this review. [ROB-P1](../../skills/domain-robotics/references/source-map.md#rob-p1)

## Supporting implementations and honest depth limits

### Finch, Aviary and LDP

Finch's notebook environment demonstrates a concrete tool loop: reset selects tools and state; a model edits notebook cells; an edit saves and reruns the notebook; submitting an answer terminates the episode. Local and Docker execution are separate configurations, and the Docker notebook path allows error outputs. Repeated cell execution can repeat an effect unless the environment restricts those cells to pure or replay-safe computation. An answer submission is not a correctness oracle. Both environment files were read, but dataset loaders, alternative experiments and hosted deployment settings were not comprehensively audited. [SCI-F1](../../skills/domain-science/references/source-map.md#sci-f1)

Aviary filters registered tool names and supports configurable concurrency and error handling. Its reader/writer lock is created within an invocation; this does not establish mutual exclusion across independent calls or processes. Synchronous tools run in threads, so a timed-out await does not itself prove a real action ended. LDP's selected rollout path preserves truncation and exceptions separately and attempts environment cleanup. These are complementary mechanisms: a bounded agent trajectory still needs an external-effect supervisor and a task-specific success predicate. [SCI-A1](../../skills/domain-science/references/source-map.md#sci-a1), [SCI-D1](../../skills/domain-science/references/source-map.md#sci-d1)

### Emerald public language and protocol surfaces

Symbolic Lab Language is a large public implementation for interacting with cloud laboratories through Mathematica notebooks. The README explicitly requires login for database operations. The inspected `ValidObjectQ` path downloads object packets and runs associated validation tests. This is useful evidence of typed domain state and validation against a database snapshot, but the snapshot can become stale before an effect. Most experiment code, the cloud scheduler, operating procedures and actual device integration were not inspected. [SCI-E1](../../skills/domain-science/references/source-map.md#sci-e1)

The separate ECL community repository contains protocol examples and contribution guidance. It is not an implementation of the commercial cloud and should not be counted as a second cloud-lab runtime. `ecl-protos`, verified and acquired after the initial list, contains a search RPC, recursively typed filters, quantities and unit expressions. Those schema declarations are valuable for a data contract but do not provide a search backend, unit-conversion implementation or instrument executor. [SCI-E2](../../skills/domain-science/references/source-map.md#sci-e2), [SCI-E3](../../skills/domain-science/references/source-map.md#sci-e3)

### Formant public interfaces

The toolkit offers data and visualization libraries on top of Formant APIs. The resources repository contains protocol definitions for telemetry, command responses, intervention requests and heartbeat streams. `PostData` explicitly distinguishes acceptance/queuing from completed upload; an intervention can exist before any operator responds. Those distinctions are useful design inputs for an inspectable workflow. A health RPC confirms interface availability, not mission success. [ROB-F1](../../skills/domain-robotics/references/source-map.md#rob-f1), [ROB-F3](../../skills/domain-robotics/references/source-map.md#rob-f3)

The ROS adapter's control module maps configured callbacks to services and publishers. The selected service coordinator has a service-availability timeout, followed by a synchronous service call with no explicit completion timeout in that method. A command path can invoke a service and then a publisher, so the integration must define compound effects and partial failure. This is a targeted code-path inspection; no claim is made about all toolkit methods, Formant's backend authorization or an actual robot's behavior. [ROB-F2](../../skills/domain-robotics/references/source-map.md#rob-f2)

### Healthcare administrative skills

The verified `ajhcs/healthcare-agents` repository supplies a progressive router, specialist prompts, handoff guidance and executable audit/evaluation tooling. The router first narrows the workflow, then loads one primary specialist and relevant full instructions. Its working ledger tracks facts, documents, policy applicability and action owners. It explicitly distinguishes source material from authority. This is a strong pattern for avoiding a giant undifferentiated prompt. [HEALTH-A1](../../skills/domain-healthcare/references/source-map.md#health-a1), [HEALTH-A2](../../skills/domain-healthcare/references/source-map.md#health-a2)

The deterministic audit checks expected headings, citation-like tokens and template/usability signals. These can detect maintenance regressions, but counting a citation cannot prove its accuracy or applicability. The evaluation README distinguishes routing, model canaries and synthetic benchmark-inspired prompts, and explicitly says the latter do not reproduce the benchmark's GUI environments. Therefore a passed pack audit would not establish clinical validity, cross-system completion or patient benefit. No such audit or model evaluation was executed during corpus acquisition. [HEALTH-A3](../../skills/domain-healthcare/references/source-map.md#health-a3), [HEALTH-A4](../../skills/domain-healthcare/references/source-map.md#health-a4)

## Model substitution and comparison suitability

For computational workflows, the tractable local comparison is to hold the capability implementations, artifact schemas, datasets, budgets and task oracle constant while varying the architecture-producing model and skill set. BioNeMo's scripts and Finch's environment make certain tool contracts inspectable; that does not mean all their external models, services or datasets are locally available. Robin's inspected path depends on hosted execution, so matching a prompt alone is not a controlled replacement experiment.

For robotics, compare generated task specifications and adapter conformance against fake devices or a fixed simulator before measuring any physical behavior. RMF's public stack supports source-level study of dispatch and state contracts. Formant's public SDKs permit inspection of integration surfaces; they do not disclose a hosted service implementation. Skild's policy is a different component from a task-workflow generator. A generator might correctly orchestrate an adapter without reproducing low-level motor intelligence.

For healthcare administration, measure routing, record reconciliation, document completeness, authority checks and downstream state using synthetic records. Separate those from language quality and any clinical result. The acquired pack can inform skills and canaries, but a prompt-only probe is not a real portal/EHR benchmark. No patient data or clinical actions are needed to test the administrative control boundary.

Freeze evaluation inputs, reference outputs, budgets and intervention policy before comparative runs. Cases inspected during skill revision are development evidence. Keep public examples separate from the sealed comparison set. Report architectural generation and runtime enforcement independently: a weak model may produce a valid workflow that the runtime safely blocks, and a strong model may produce an attractive but unsupported claim.

## Implementation handoff and limits

The three original domain skills provide a workflow-construction process, progressive references, state/effect requirements, intervention handling and an explicit output contract.
