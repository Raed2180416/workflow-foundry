# Separate the historical question from the current-world question

## Executed separation witness

`run-001/RESULTS.json` records one native execution, zero model calls, and a catalog-only intervention. The wrong JSON artifact is published by a terminal successful run. Adding one unused, pure local capability changes the full registry hash but no existing descriptor, source file, artifact byte, run or event. The historical receipt remains readable; current verification and repair refuse `OUTCOME_CONTRACT_BINDING`; re-registering the identical expectation refuses `OUTCOME_CONTRACT_CONFLICT`. Restoring the original catalog restores verification. The control never dispatches the added capability.

This is conservative existing behavior, not lost or rewritten history. It reveals that a useful historical assessment and current operational eligibility are coupled in the current `verify` method. The reviewed source already has a test expecting unused-addition refusal. The new experiment diagnoses its consequence rather than claiming a previously unseen source defect.

Let E be the immutable expected JSON, B the preserved bytes, O the exact observer semantics, and X the recorded request/proposal/run/event bindings. A historical content assessment is H(E,B,O,X). A future execution claim additionally depends on the actual candidate, environment, policy, evidence and authority. A changed live catalog does not by itself change E or B. Conversely, H remaining valid says nothing about whether the next workflow is safe, realizable or successful under a new catalog.

The first implementation is therefore a distinct read-only historical inspector, not deletion of the old registry checks. It must verify the old hashes and full causal record, recompute only the supported recorded JSON assessment, retain unknown observer/absence cases, and explicitly decline current-world qualification. Its result must not be accepted as the old coordinator's repair receipt or an application permit. Physical filesystem availability is a separate observation: preserved bytes are historical evidence even when a live file later changes.

## Counterexamples that rule out the tempting shortcuts

The source review in `../outcome-dependency-review-20260917/NOTE.md` gives precise locations. An unchanged artifact writer can receive wrong upstream data. A repaired branch can call a tool absent from the old trace. Equal function text can hide different closure state or remote behavior. Approval, evidence freshness, cost and schema metadata matter even with unchanged handler code. A new MCP component can change every external descriptor and launch processes, unlike this pure local registration. For missing files, a completed producer of a different file may establish namespace loss; retaining only target producers can incorrectly turn unknown into unsatisfied. The old registry hash does not reconstruct an old per-capability snapshot.

Therefore no used-tool compatibility or cross-registry promotion is claimed. A later continuation protocol must preserve the existing semantic expectation and root lineage while explicitly binding fresh candidate/environment qualification. Creating a new root merely to evade the old uniqueness constraint would hide the problem rather than solve it.

## Where bounded semantic judgment belongs

The exact replay of a frozen JSON predicate needs no model. Jev could help interpret a subsequent correction as an expectation change, a method change, or missing evidence, or assess which assumptions are implicated by a world change. Those are probabilistic semantic judgments to test against separation witnesses. They cannot grant execution authority, authenticate an old record, or replace deterministic identity checks. No Jev inference has been run in this continuation because the current supported execution context lacks gateway authentication.
