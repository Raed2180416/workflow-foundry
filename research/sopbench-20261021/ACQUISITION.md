## What was fetched

The clone only. 381 files: the `amazon_sop_bench` package source (agents, evaluation, benchmarks, tools, CLI), docs, examples,
tests, and `src/amazon_sop_bench/benchmarks/data/<sop>/` for 14 SOPs (sop.txt, toolspecs.json, tools.py, metadata.json,
test_set_with_outputs.csv, mostly test_set_without_outputs.csv, some data.csv, croissant.json, LICENSE.md, disclaimer.txt,

## Runtime for the mock tools (pinned, no package install)

The 14 `tools.py` files import only the standard library, `pandas` and `python-dateutil`; one imports
`amazon_sop_bench.utils.logging` (stubbed by our loader). We do not install SOP-Bench. A separate venv holds exactly these

- wheels (sha256 from PyPI, fetched 2026-10-21): numpy 2.1.3 (cp313 manylinux x86_64), pandas 2.2.3 (cp313 manylinux x86_64),

  Upstream pins only lower bounds (`pandas>=2.0.0`); these are our choice, recorded so a rerun is byte-identical.

## How upstream code runs here

- Only through `experiments/sopbench/bridge.py`, with the venv interpreter in isolated mode (`python -I`), from a neutral
  working directory under `/var/tmp/foundry-work/sopbench/`, with a minimal environment (`PATH`, `LANG`, `LC_ALL`, `TZ`, a
  private `HOME`, `PYTHONHASHSEED=0`) and the clone path passed as an argument. `sys.dont_write_bytecode` keeps the clone
  free of `__pycache__`.
- Upstream modules are loaded by file path (`experiments/sopbench/upstream.py`): `types.py`, `tools/base.py`,
  `tools/manager.py`, `benchmarks/registry.py`, `benchmarks/loader.py`, `benchmarks/__init__.py`, `evaluation/parser.py`,
  `evaluation/metrics.py`, `evaluation/evaluator.py`, `agents/base.py`. No package `__init__` runs, so neither the CLI,
  the Bedrock/LangChain agents, `dotenv` (which would read a `.env`) nor `rich` is imported. Stubbed: `utils/logging.py`
  (stdlib logger), `config.py` (`save_traces=False`), `evaluation/reporter.py`.
- Each SOP's `tools.py` runs exactly as upstream's loader runs it (`loader.py:254-302`), except that its `pd` attribute is a
  proxy serving the SOP's CSV files from a host cache filtered to the run's rows (NOTES.md §3).
- No model was called for anything in this record; no credential reaches the bridge, and the bridge needs none.

## Incidents

- During inspection (2026-10-21, before the bridge existed) one interpreter was started **without** `-I` with its working
  directory inside the clone (`src/amazon_sop_bench/`): `python3 -c "import pandas"`. The clone's `types.py` shadowed the
  standard library `types` module; Python executed that file's first import lines and failed with a circular-import error.
  `types.py` holds only dataclass and enum definitions (read before and after); nothing else of upstream ran. It left
  `__pycache__` directories, since removed. Every later interpreter ran from a neutral directory with `-I`.
- While stopping a slow parity run (2026-10-21 ~11:55 UTC) a `pgrep -af bridge.py | xargs kill` also matched bridge
  processes by name. A concurrent session's AutomationBench test (`/tmp/autobench-h-guards-*`) was running at the time; if
  one of its bridge processes was killed, that session saw a spurious failure then. Later stops used recorded PIDs only.
